BloodHound sends a signed HTTPS POST request to a generic webhook destination when a collector remains offline. Use this reference to validate the request, route the event, and process it safely. For setup instructions, see [Configure webhook alerts](/manage-bloodhound/alerts/configure).

<BetaAccessNote feature="Alerts" />

## Supported event

| Event | Identifier | Data version | Trigger |
| --- | --- | --- | --- |
| Collector Offline | `collector.status.offline` | `1` | A collector has not checked in for at least 20 minutes. |

BloodHound evaluates the condition about every seven minutes. It suppresses another event for the same collector for seven days and does not issue a recovery event.

## Receive the request

BloodHound sends a JSON request with these headers:

| Header | Purpose |
| --- | --- |
| `Content-Type: application/json` | Identifies the request body format. |
| `X-Bloodhound-Signature` | Carries the signature timestamp and HMAC-SHA256 signature. |
| `X-Bloodhound-Event-Type` | Lets your receiver route the event without parsing the body. |
| `X-Bloodhound-Event-ID` | Identifies the event for idempotent processing. |

Return a 2xx response after your receiver accepts the event. BloodHound treats every other HTTP status, including redirects, as a failed delivery.

## Payload schema

The envelope stays stable across event versions. The `version` field identifies the shape of `data`.

| Field | Type | Description |
| --- | --- | --- |
| `event_id` | UUID | Stable event identifier. It matches `X-Bloodhound-Event-ID`. |
| `event_type` | string | `collector.status.offline`. |
| `version` | integer | Payload data version. This event uses `1`. |
| `timestamp` | RFC 3339 timestamp | Time BloodHound created the event. |
| `message` | string | Human-readable summary. |
| `data` | object | Collector details for the event. |

Version 1 includes these fields in `data`:

| Field | Description |
| --- | --- |
| `collector_id` | Stable collector identifier. |
| `name` | Collector name. |
| `hostname` | Collector host name. |
| `ip_address` | Collector IP address. |
| `type` | Collector type: `azurehound`, `sharphound`, or `openhound`. |
| `version` | Collector software version. |
| `last_checkin` | Collector's last check-in time in RFC 3339 UTC format. |
| `created_at` | Time the collector record was created. |
| `updated_at` | Time the collector record was last updated. |
| `auth_type` | Collector authentication type: `bloodhound` or `windows`. |
| `issuer_address` | Collector issuer address. |
| `issuer_address_override` | Collector issuer address override. |

<Warning>
The payload can include infrastructure and collector metadata. Protect the receiving endpoint, restrict who can access stored payloads, and do not send the payload to an unapproved third party.
</Warning>

## Verify the signature

BloodHound signs the exact raw request body with your webhook's HMAC secret. The signature header has this format:

```text
t=<unix-timestamp>,v1=<hex-hmac-sha256>
```

The signed value is the timestamp, a period, and the unmodified request body:

```text
HMAC-SHA256(secret, "{t}.{raw body}")
```

Do not parse and reserialize JSON before verification. That changes the body and invalidates the signature.

```python
import hashlib
import hmac
import time


def verify_bloodhound_webhook(raw_body, signature_header, secret):
    parts = dict(part.split("=", 1) for part in signature_header.split(","))
    timestamp = parts["t"]
    supplied_signature = parts["v1"]

    # Reject stale requests to reduce replay risk. Choose a window that suits
    # your receiver; this example allows five minutes.
    if abs(time.time() - int(timestamp)) > 300:
        return False

    signed_payload = timestamp.encode() + b"." + raw_body
    expected_signature = hmac.new(
        secret.encode(), signed_payload, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected_signature, supplied_signature)
```

**Node.js**

```javascript
import crypto from "node:crypto";

function verifyBloodHoundWebhook(rawBody, signatureHeader, secret) {
  const parts = Object.fromEntries(
    signatureHeader.split(",").map((part) => part.split("=", 2))
  );
  const timestamp = parts.t;
  const suppliedSignature = parts.v1;

  if (!timestamp || !suppliedSignature) return false;
  if (Math.abs(Date.now() / 1000 - Number(timestamp)) > 300) return false;

  const expectedSignature = crypto
    .createHmac("sha256", secret)
    .update(timestamp)
    .update(".")
    .update(rawBody)
    .digest("hex");

  const expected = Buffer.from(expectedSignature, "hex");
  const supplied = Buffer.from(suppliedSignature, "hex");
  return supplied.length === expected.length && crypto.timingSafeEqual(expected, supplied);
}
```

Also use `event_id` to make processing idempotent. A retry preserves the event ID and payload timestamp but has a new signature timestamp.

## Delivery behavior

| Behavior | Value |
| --- | --- |
| Request method | HTTPS POST |
| Success response | Any 2xx HTTP response |
| Request timeout | 7 seconds |
| TLS requirement | TLS 1.2 or later |
| Redirects | Not followed; treated as failed delivery |
| Automatic retries | Up to seven total attempts: the initial delivery and up to six retries |
| Retry timing | The first retry is scheduled after up to about six minutes. Each later retry uses a 4x backoff with up to 20% subtract-only jitter. The retry worker runs about every six minutes. |
| Retry processing | The retry worker processes up to 30 due deliveries per run. A backlog can delay a retry beyond its scheduled time. |
| Failed final delivery | The delivery is dead-lettered and receives no further automatic retries. |
| Event History retention | Events and their delivery attempts are retained for 90 days. |

After the final failed attempt, use Event History or the [retry attempt API](/reference/alerts/retry-alert-attempt) to investigate and requeue a failed delivery. Manually requeuing a dead-lettered delivery gives it one additional send attempt; if that attempt fails, BloodHound dead-letters it again.

## Webhook health

BloodHound Enterprise represents webhook health as a rolling score from `0` to `1`, where `1.0` is fully healthy. The API returns this value in the webhook's `health` field. Each webhook starts with a health score of `1.0`.

BloodHound Enterprise calculates the score as an exponentially weighted moving average of dispatch results. Each result has a weight of `0.1`: successful dispatches increase the score and failed dispatches decrease it.

The **Delivery** page displays the score as a color-coded percentage badge in the **Health** column. The **Webhook Details** view displays the same badge. A score of `0.9` or higher is green, a score from `0.7` to less than `0.9` is yellow, and a score below `0.7` is red.

BloodHound Enterprise automatically disables a webhook when its health falls below `0.5`, which occurs after roughly seven consecutive failed dispatches. Health changes only after production dispatches; test requests do not affect the score. Review and correct the receiver before you re-enable the webhook. Re-enabling the webhook resets its health score to `1.0`.
