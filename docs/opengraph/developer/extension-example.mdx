An OpenGraph extension definition schema tells BloodHound how to display, scope, and analyze custom graph data. In this tutorial, you'll build a small sample extension that models an identity control path:

```text
User A -> Group B -> User C -> Server D -> Domain Admin
```

In this model, every identity or asset is a node. Every group membership, permission, and session is an edge that connects two nodes. Because BloodHound evaluates traversable edges transitively, a standard user can still control a critical identity through a chain of relationships. This is a structural failure of the least privilege principle.

Follow the examples in this tutorial in order. Each section adds incremental capabilities to the same sample extension so that you can:

- See how the schema and payload work together
- Understand how BloodHound uses the schema to render and analyze the payload

By the end of this tutorial, you'll have a sample extension definition schema and matching payload that:

- Defines extension metadata with the `schema` object
- Defines an environment to establish analysis scope
- Styles nodes with display kinds
- Identifies principal kinds for pathfinding and <Tooltip tip="Exposure and impact">metrics calculation</Tooltip>
- Makes relationships traversable for attack path analysis
- Adds custom Entity Panel content to a relationship kind
- Adds a Privilege Zone target for finding evaluation
- Defines relationship findings with context and remediation guidance in BloodHound Enterprise

## Define the schema object

Every extension definition schema starts with a top-level [`schema`](/opengraph/developer/graph-definition#schema) object. Define this object first because it establishes the extension's name, version, and namespace, which the rest of this tutorial reuses.

<Tabs>
  <Tab title="Example definition">
  The following example shows the minimum required fields for a valid extension definition schema. BloodHound rejects a schema upload where `node_kinds` is empty, so this example defines a single `EX_Domain` node kind. The `relationship_kinds` array is empty because this is the first iteration of the schema.

  ```jsonc title="example-extension-definition.json"
  {
    "schema": {
      "name": "ExampleExtension",
      "display_name": "Example Extension",
      "version": "v1.0.0",
      "namespace": "EX"
    },
    "node_kinds": [
      {
        "name": "EX_Domain",
        "display_name": "Example Domain"
      }
    ],
    "relationship_kinds": []
  }
  ```

  - [`schema.name`](/opengraph/developer/graph-definition#param-name) uniquely identifies this extension in BloodHound. Uploading a schema with a matching `schema.name` and a newer `schema.version` overwrites the existing extension definition schema.
  - [`schema.display_name`](/opengraph/developer/graph-definition#param-display-name) is the human-readable label shown for the extension in BloodHound.
  - [`schema.version`](/opengraph/developer/graph-definition#param-version) tracks the extension schema version and must use v-prefixed semantic versioning, for example `v1.0.0`.
  - [`schema.namespace`](/opengraph/developer/graph-definition#param-namespace) is the prefix, `EX`, applied to every `name` field you define later in this tutorial (for example, `EX_Domain` and `EX_MemberOf`) to avoid collisions with built-in graph elements and other extensions.
  - [`node_kinds`](/opengraph/developer/graph-definition#node_kinds) requires at least one entry. BloodHound rejects a schema upload where `node_kinds` is empty, even if `relationship_kinds` is populated.

  <Warning>
    **Uploading schema iterations**

    As you follow this tutorial and [upload](/opengraph/extensions/manage#update-an-extension) each iteration of the sample schema, increment `schema.version` before every upload. BloodHound rejects an upload that reuses the same `schema.name` and `schema.version` pairing as an already-installed schema, so you cannot re-upload an unchanged version to pick up new edits.

    For example, bump the version from `v1.0.0` to `v1.0.1` (or higher) each time you add the node kinds, relationship kinds, environments, or findings from the following sections and re-upload the schema.
  </Warning>

  The remaining sections in this tutorial build on this `schema` object by adding `node_kinds`, `relationship_kinds`, `environments`, and `relationship_findings` entries.
  </Tab>
  <Tab title="Example payload">
  The payload is a separate JSON object that contains the graph data you want BloodHound to ingest and analyze.

  Don't worry about uploading the payload yet. This section shows the minimum required fields for a valid payload, which is empty because the schema does not yet define any relationship kinds, and no node instances have been added yet.
  
  <Note>
    The payload must include a [`metadata.source_kind`](/opengraph/developer/metadata#param-source-kind) value that matches the `schema.namespace` value in the extension definition schema.
  </Note>

  ```jsonc title="example-extension-payload.json" highlight={3}
  {
    "metadata": {
      "source_kind": "EX"
    },
    "graph": {
      "nodes": [],
      "edges": []
    }
  }
  ```
  </Tab>
  <Tab title="BloodHound behavior">
  BloodHound does not display any graph data because the payload is empty. However, you can still upload the schema to BloodHound to see how the extension appears in the UI.
  
  The extension's display name appears in the **Active Extensions** list on the **OpenGraph Extension Management** page.

## Define environments

<img
  noZoom
  src="/assets/enterprise-edition-pill-tag.svg"
  alt="Applies to BloodHound Enterprise only"
  style={{ "width":"20%" }}
/>

Use [`environments.environment_kind`](/opengraph/developer/graph-definition#param-environment-kind) to tell BloodHound which node kind represents an environment for organization, filtering, and analysis.

In a custom extension, this behavior comes from the environment node kind you define in the schema and then reference from the payload. In the UI, this schema definition enables environment selection controls on the following pages:

- **Attack Paths**
- **Posture**
- **Zone Builder**

<FeatureFlagNote />

<Tabs>
  <Tab title="Example definition">
  This example builds on the `EX_Domain` node kind from the previous section. In this example, the `EX_Domain` node kind becomes the environment kind for a new `environments` object (both are necessary to complete the definition).
  
  The `EX_User` node kind is a principal that can be evaluated within that environment.

  ```jsonc title="example-extension-definition.json"
  {
    "schema": {
      "name": "ExampleExtension",
      "display_name": "Example Extension",
      "version": "v1.0.1",
      "namespace": "EX"
    },
    "node_kinds": [
      {
        "name": "EX_Domain",
        "display_name": "Example Domain"
      },
      { // [!code ++:4]
        "name": "EX_User",
        "display_name": "Example User"
      }
    ],
    "relationship_kinds": [],
    "environments": [ // [!code ++:7]
      {
        "environment_kind": "EX_Domain",
        "source_kind": "EX",
        "principal_kinds": ["EX_User"]
      }
    ]
  }
  ```
  </Tab>
  <Tab title="Example payload">
  It's important to include the [`metadata.source_kind`](/opengraph/developer/metadata#param-source-kind) value in the payload so that BloodHound can associate the payload with the schema definition. This helps facilitate organizing and managing graph data by [source](/opengraph/developer/graph-data#data-source), which is especially useful for monitoring [data quality](/collect-data/data-quality).
  
  The [`properties.environmentid`](/opengraph/developer/nodes#param-properties-environmentid) and [`properties.collected`](/opengraph/developer/nodes#param-properties-collected) values on the environment node are required for BloodHound to recognize the environment and scope analysis correctly.

  <Note>
    **What does "collected" mean?**

    The `properties.collected` value only applies to environment node kinds. It indicates whether a collector actually ran against that environment, as opposed to the environment node existing because another collection run discovered a reference to it.

    For example, SharpHound can discover a domain through a trust relationship without running against that domain directly. In that case, BloodHound creates a node for the discovered domain, but its contents remain unknown, so `collected` should be `false`. Set `collected` to `true` only for environments where the collector ran directly.
  </Note>

  ```jsonc title="example-extension-payload.json"
  {
    "metadata": {
      "source_kind": "EX"
    },
    "graph": {
      "nodes": [
        { // [!code ++:10]
          "id": "example-domain-1",
          "kinds": ["EX_Domain"],
          "properties": {
            "name": "corp.example.local",
            "displayname": "Corp Example Domain",
            "environmentid": "example-domain-1",
            "collected": true
          }
        },
        { // [!code ++:9]
          "id": "example-user-a",
          "kinds": ["EX_User"],
          "properties": {
            "name": "user-a",
            "displayname": "User A",
            "environmentid": "example-domain-1"
          }
        }
      ]
    }
  }
  ```
  </Tab>
  <Tab title="BloodHound behavior">
  The example definition and payload work together to create an environment that scopes analysis for the `EX_User` principal kind.

  - The payload's `metadata.source_kind` value registers `EX` as a source kind and applies it to each node in the payload.
  - BloodHound can organize extension data under the environment represented by `EX_Domain` and expose that environment through the relevant environment selector and filters in the UI.
  - Nodes associated with that environment through `properties.environmentid` are evaluated within that scope.
  - In BloodHound Enterprise, the same environment definition also scopes findings and metrics when the other required analysis conditions are met.
  - If the environment node kind is missing from the schema, or if payload nodes do not point to the environment node through `properties.environmentid`, the environment does not appear or scope data as expected.

## Define node styling

The [`is_display_kind`](/opengraph/developer/graph-definition#param-is-display-kind) field controls a node's visual appearance in the graph.

- Use `true` on the kind that should supply the node's icon and color.
- Use `false` for secondary kinds that help classify the node but should not define its appearance.

This example builds on the environment definition from the previous section by styling the existing `EX_Domain` and `EX_User` node kinds and adding group, computer, domain admin, and high-value classification kinds.
<Tabs>
  <Tab title="Example definition">
  Add `is_display_kind`, `icon`, and `color` to the existing `EX_Domain` and `EX_User` node kinds, then add the `EX_DomainAdmin`, `EX_Group`, `EX_Computer`, and `EX_HighValue` node kinds to the schema to support the example scenario.

  The first five node kinds are display kinds that control the node's icon and color. The last node kind is a secondary classification kind that does not control the node's appearance.

  ```jsonc title="example-extension-definition.json"
        "name": "EX_Domain",
  ```

  <Tab title="BloodHound behavior">
  The example definition and payload work together to create a graph that uses display kinds to control node styling.

  - `EX_User`, `EX_Group`, `EX_Computer`, and `EX_DomainAdmin` define distinct visual styles for User A, Group B, Server D, and Domain Admin.


## Define principals

<img
  noZoom
  src="/assets/enterprise-edition-pill-tag.svg"
  alt="Applies to BloodHound Enterprise only"
  style={{ "width":"20%" }}
/>

The [`principal_kinds`](/opengraph/developer/graph-definition#param-principal-kinds) field identifies which node kinds BloodHound Enterprise should treat as <Tooltip tip="An entity that can authenticate, be assigned permissions, and serve as a basis for risk metric calculations">principals</Tooltip> inside an environment.

This setting affects analysis scope. If a node kind is not listed in `principal_kinds`, BloodHound Enterprise can still ingest and display those nodes, but BloodHound Enterprise does not treat them as principals for findings and <Tooltip tip="(Exposure and impact)">metrics calculation</Tooltip> in that environment.

<Tabs>
  <Tab title="Example definition">
  This example builds on the previous definition by adding the computer and domain admin node kinds to `principal_kinds`.

  Do not include `EX_Group` in `principal_kinds` for this example. Group B is still an important node in the path because it receives permissions and passes control through the `EX_MemberOf` edge, but it does not authenticate as an identity. BloodHound can still traverse through Group B when the relationship kinds are traversable.

  <Note>
    **Findings and metrics**

    The `principal_kinds` definition does not create findings by itself, and the payload does not include a separate finding object.

    BloodHound Enterprise derives the finding from the environment definition, the [traversable relationship kind](/opengraph/developer/extension-example#define-relationships), the [Privilege Zone target](/opengraph/developer/extension-example#create-a-privilege-zone-rule), the matching [relationship findings](/opengraph/developer/extension-example#define-relationship-findings) definition, and the uploaded graph data.

## Define relationships

Use [`relationship_kinds.is_traversable`](/opengraph/developer/graph-definition#param-is-traversable) to control whether edges of a relationship kind are used for pathfinding and Attack Path detection.

When you set `is_traversable` to `true` on a relationship kind, every edge of that kind inherits the same traversability behavior. Use traversable relationships to represent conditions where the starting node can take control of the ending node to a degree that lets an attacker abuse the ending node's outgoing edges.

<Tabs>
  <Tab title="Example definition">
  Each relationship is traversable because it represents a control transition. Auditing User A in isolation shows a standard user, but tracing the edges shows that User A can reach the Domain Admin identity.

  ```jsonc title="example-extension-definition.json"
        "icon": "user",
        "color": "#d33115"

        "icon": "user",
        "color": "#b42318"
      },
  ```

## Create a Privilege Zone rule

<img
  noZoom
  src="/assets/enterprise-edition-pill-tag.svg"
  alt="Applies to BloodHound Enterprise only"
  style={{ "width":"20%" }}
/>

Use [Privilege Zones](/analyze-data/privilege-zones/overview) to identify which graph objects represent higher-privilege targets. BloodHound Enterprise generates Attack Path findings when a lower-privileged principal can reach a higher-privileged zone through traversable relationships.

This example builds on the relationship payload from the previous section. The schema and payload define the path from User A to the Domain Admin identity, but the Domain Admin identity must be in a higher Privilege Zone before BloodHound Enterprise can treat the path as a finding.

<Steps>
  <Step title="Open the pathfinding graph">
    Use the [Pathfinding](/analyze-data/explore/search#pathfinding) tab on the **Explore** page to display the path from `User A` to `Domain Admin` from the previous example.
  </Step>
  <Step title="Open the Domain Admin context menu">
    Right-click the `Domain Admin` node in the graph to open the [context menu](/analyze-data/explore/search#context-menu).
  </Step>
  <Step title="Add Domain Admin to Tier Zero">
    Select **Add to Tier Zero**. BloodHound Enterprise adds the Domain Admin identity to the Tier Zero Privilege Zone and starts analysis.
  </Step>
  <Step title="Wait for analysis">
    Wait for analysis to finish before proceeding to the next step.
  </Step>
</Steps>

After analysis, the example data contains the required privilege boundary:

- User A is a lower-privileged `EX_User` principal.
- Group B has full control over User C through a traversable permission edge.
- User C is a local administrator on Server D.
- Server D hosts a session for the Domain Admin identity.
- The Domain Admin identity is a Tier Zero target.

With that boundary in place, the traversable path `User A -> Group B -> User C -> Server D -> Domain Admin` can generate a finding when the schema includes a matching `relationship_findings` definition. Continue to the next section to define that finding.

## Next steps

Use these examples as a checklist when you design an OpenGraph extension definition schema. Start with the environment model, then add the node kinds, relationship kinds, Privilege Zone targets, and finding definitions that BloodHound needs to display, scope, and analyze your data.

- Review the full [extension definition schema reference](/opengraph/developer/graph-definition) before you define your schema fields.
- Build a matching [graph data payload](/opengraph/developer/graph-data) that uses the node kinds, relationship kinds, environment IDs, and source kind from your schema.
- Check the [node](/opengraph/developer/nodes) and [edge](/opengraph/developer/edges) requirements when you prepare data for ingestion.

## Troubleshoot

The following conditions may lead to unexpected behavior when you create an OpenGraph extension:

- The node or relationship kind name does not exactly match the schema definition.
- Kind names are not properly [namespaced](/opengraph/developer/graph-definition#namespacing) (for example, missing the `namespace_` prefix) and cause schema upload validation failures.
- The `tag` namespace prefix is used in a kind name. BloodHound rejects schema uploads that use this reserved prefix in any letter case (`tag`, `Tag`, `TAG`).
- The [`schema.version`](/opengraph/developer/graph-definition#param-version) value does not use v-prefixed semantic versioning (for example, `v1.0.0`). BloodHound rejects schema uploads that use a different format.
- The environment node exists, but `properties.collected` is not set to `true`.
- Nodes are missing `properties.environmentid`.
- The environment or payload does not include a registered `source_kind`.
- The relationship kind is not traversable.
- The expected node kind is not included in `principal_kinds`.
- The target node is not in the expected Privilege Zone.
- The finding definition references the wrong `environment_kind` or `relationship_kind`.
