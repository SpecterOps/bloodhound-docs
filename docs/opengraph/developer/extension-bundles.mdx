<Warning>
  This is internal guidance for SpecterOps extension authors. It describes the current v9.8.0 implementation state. The implementation supports all three bundle components, but GitHub, Okta, and Jamf are not yet published as bundle artifacts.
</Warning>

An **extension bundle** is a ZIP archive that packages an OpenGraph extension definition schema with the extension-managed assets that BloodHound installs with it.

The bundle gives one extension one installable artifact and gives the platform a single source of truth for the extension's schema and managed assets.

## Implementation status

The ZIP parser is implemented in the [`PUT /api/v2/extensions`](https://bloodhound.specterops.io/reference/opengraph-experimental/upserts-the-opengraph-extension) upload path for Community and Enterprise. The BloodHound Enterprise startup loader also accepts ZIP bundles.

<Warning>
  Bundle support is available through the extension API and, for BloodHound Enterprise, the embedded extension startup loader. An extension's release and publication workflow must still be updated before that extension can adopt a ZIP artifact.
</Warning>

| Component | Current implementation state | Author action for v9.8.0 |
|---|---|---|
| `schema.json` | Required and installed through the API and startup loader. | Keep the extension definition schema as the bundle's required component. |
| `pz_rules.json` | Parsed and reconciled with the extension through the API and BHE startup loader. When the `tier_management_engine` feature flag is disabled, the rules are skipped. | Include the component when the extension manages Privilege Zone rules and the target deployment has tier management enabled. |
| `saved_queries.json` | Parsed and reconciled with the extension through the API and BHE startup loader. Extension-managed queries are public and read-only. | Include the component when the extension manages saved queries. |

The implementation supports schema, Privilege Zone rules, and saved queries in one bundle. The current BHE publication artifacts for GitHub, Okta, and Jamf remain JSON files, so their bundle adoption is a release-process decision rather than a parser limitation.

Do not change the production GitHub, Okta, or Jamf artifacts from JSON to ZIP until each extension's publication workflow has been updated and the resulting artifact has been verified through every supported consumer.

An upload that returns success confirms that the bundle was accepted and its contents were processed. If tier management is disabled, a supplied `pz_rules.json` component is skipped; verify the installed extension and managed assets after installation.

## ZIP archive structure

Place the recognized component files at the root of the ZIP archive:

<Tree>
  <Tree.Folder name="<extension-name>-v<version>.zip" defaultOpen>
    <Tree.File name="schema.json" />
    <Tree.File name="pz_rules.json" />
    <Tree.File name="saved_queries.json" />
  </Tree.Folder>
</Tree>

The following rules apply to the archive:

- `schema.json` is required.

- `pz_rules.json` and `saved_queries.json` are optional. If a component is omitted from an extension update, reconciliation removes the existing extension-managed assets of that type.

- Use the exact root-level file names. Nested files, documentation files, checksums, and other extra files are rejected as unexpected components.

- Include each component at most once. Duplicate component names are rejected.

- For the BHE API, keep each recognized component at or below the 10 MiB decompressed component limit.

- Keep the optional components separate from `schema.json`. A `schema.json` file that embeds `pz_rules` or `queries` is rejected when it is uploaded as part of a bundle.

The schema itself keeps the existing [extension definition schema](https://bloodhound.specterops.io/opengraph/developer/graph-definition) format. A minimal schema-only bundle is valid when `schema.json` contains the required `schema`, `node_kinds`, `relationship_kinds`, and any applicable `environments` and `relationship_findings` definitions.

<Note>
  If `schema.json` declares relationship findings, both the API and the BHE startup loader require `pz_rules.json` with at least one rule.

  This requirement applies even when the target deployment has tier management disabled. In that case, the bundle can be accepted but the PZ rules are skipped during upsert.
</Note>

## Privilege Zone rule contract

The current parser contract for `pz_rules.json` is a single JSON object containing a `pz_rules` array. Each rule requires a stable `key`, a name, and exactly one Cypher seed. `enabled` and `allow_disable` are optional and default to `true`.

```json title="pz_rules.json"
{
  "pz_rules": [
    {
      "key": "github-tier-zero-principals",
      "name": "GitHub: Tier Zero principals",
      "description": "Identifies GitHub principals assigned to Tier Zero.",
      "enabled": true,
      "allow_disable": true,
      "seeds": [
        {
          "type": 2,
          "value": "MATCH (n:GH_User) WHERE n.tier = 0 RETURN n"
        }
      ]
    }
  ]
}
```

<Note>
  OpenHound currently uses a different rule-file contract. Its [`PrivilegeZone` model](https://github.com/SpecterOps/OpenHound/blob/main/src/openhound/core/models/privilege_zone.py#L9-L18) requires `zone`, `enabled`, `allow_disable`, and `cypher`. Its [BloodHound destination](https://github.com/SpecterOps/OpenHound/blob/main/src/openhound/destinations/bloodhound/destination.py#L89-L102) maps those fields to rule definitions.

  Do not copy those fields into this component. The bundle contract uses `key`, `enabled`, and `allow_disable`; it does not use `auto_certify`.
</Note>

<ResponseField name="pz_rules" type="array" required>
  Array of bundle Privilege Zone rule objects. Include at least one rule when `schema.json` declares relationship findings. BloodHound enforces this requirement in [bundle validation](https://github.com/SpecterOps/bloodhound-enterprise/blob/main/bhce/cmd/api/src/api/v2/opengraphschema.go#L142-L148).
</ResponseField>
<ResponseField name="pz_rules[].key" type="string" required>
  Stable identifier used to reconcile the rule on later extension upserts. The value cannot be empty or duplicated in the component.
</ResponseField>
<ResponseField name="pz_rules[].name" type="string" required>
  Unique name for the Privilege Zone rule. The value cannot be empty or whitespace-only.
</ResponseField>
<ResponseField name="pz_rules[].description" type="string">
  Optional description of the rule's purpose or the principals it identifies.
</ResponseField>
<ResponseField name="pz_rules[].enabled" type="boolean">
  Optional enabled state. Defaults to `true` when omitted.
</ResponseField>
<ResponseField name="pz_rules[].allow_disable" type="boolean">
  Optional setting that controls whether users can disable the rule. Defaults to `true` when omitted.
</ResponseField>
<ResponseField name="pz_rules[].seeds" type="array" required>
  Exactly one seed object that identifies the principals included by the rule.
</ResponseField>
<ResponseField name="pz_rules[].seeds[].type" type="integer" required>
  Seed type. Use `2` for a Cypher query that returns seed objects.
</ResponseField>
<ResponseField name="pz_rules[].seeds[].value" type="string" required>
  Cypher query used to identify the seed objects. The value cannot be empty and must parse as valid Cypher.
</ResponseField>

## Saved queries contract

The current parser recognizes `saved_queries.json` as an object with a top-level `queries` array—not a top-level `saved_queries` property.

The upsert path associates created queries with the extension, makes them public and read-only, and reconciles the submitted set. Omitting the component produces an empty query set, so an update removes existing extension-associated queries.

<Note>
  Extension-managed saved queries cannot be modified or deleted through the Saved Query APIs. Update them by submitting a new extension bundle.
</Note>

```json title="saved_queries.json"
{
  "queries": [
    {
      "query_key": "github-critical-repositories",
      "name": "GitHub: Critical repositories",
      "query": "MATCH (n:GH_Repository) WHERE n.critical = true RETURN n",
      "description": "Lists repositories marked as critical.",
      "category": "GitHub"
    }
  ]
}
```

<ResponseField name="queries" type="array" required>
  Array of saved query objects.
</ResponseField>
<ResponseField name="queries[].query_key" type="string" required>
  Stable, unique identifier for the saved query within the extension. The value cannot be empty or duplicated in the component.
</ResponseField>
<ResponseField name="queries[].name" type="string" required>
  Display name for the saved query. The value cannot be empty or duplicated in the component.
</ResponseField>
<ResponseField name="queries[].query" type="string" required>
  Cypher query to save. The value cannot be empty and must parse as valid Cypher.
</ResponseField>
<ResponseField name="queries[].description" type="string">
  Optional description of the saved query.
</ResponseField>
<ResponseField name="queries[].category" type="string">
  Optional category used to organize the saved query.
</ResponseField>

## Prepare GitHub, Okta, and Jamf for adoption

Until each extension's publication workflow is updated to produce a bundle, keep its current source layout and publication flow:

- Keep `extension/schema.json` as the source schema.
- Keep the existing `extension/privilege_zone_rules` files and `extension/saved_searches` files for the manual extension installation workflows.
- Do not replace the standalone files with a ZIP artifact in the BHE extension artifact pipeline.

Extension asset upload is required only for the schema-only workflow. If a bundle includes `pz_rules.json` or `saved_queries.json`, those managed assets are installed and reconciled through the bundle; do not upload them separately.

When an extension's release process is ready, generate a ZIP whose root contains the schema and any finalized managed components. Test the same ZIP through both consumers:

1. Upload it through `PUT /api/v2/extensions` with an accepted ZIP content type.
1. Load it through the BHE embedded extension directory used by the startup loader.
1. Verify the installed extension version and confirm that Privilege Zone rules and saved queries reconcile on both first install and update.
1. Update the `bhe-extensions` publication artifact and the BHE Dockerfile versioned artifact references together.
