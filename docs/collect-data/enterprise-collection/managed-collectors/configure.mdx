Use a collection plan to define the AWS credentials, collection scope, and daily schedule for a managed OpenHound collector. After the complete workflow is available in your tenant, use on-demand collection and its history indicators to validate the credential and confirm collection activity.

## Prepare your AWS environment

Before you configure a plan, complete the following prerequisites:

- Your BloodHound Enterprise tenant has Managed Collectors enabled by SpecterOps.
- You are signed in with an account that has permission to manage collector jobs.
- You have an AWS access key ID and secret access key for a collection principal.
- The collection principal has the required read-only permissions for your target AWS account or organization. Follow [Configure AWS permissions](/openhound/collectors/aws/configure-permissions).
- You know the AWS account and collection scope that the plan should use.

<Note>
  Managed Collectors runs the collector for you. Do not install a self-deployed OpenHound collector for this workflow. Use the self-deployed [AWS collector documentation](/openhound/collectors/aws/overview) when you need to operate OpenHound in your own environment.
</Note>

<Warning>
  The beta uses an AWS access key and secret access key. Cross-account IAM role assumption through AWS Security Token Service (STS) is not a Managed Collectors beta authentication option. Confirm support for your intended AWS scope with your SpecterOps account team before you configure a plan.
</Warning>

## Configure a collection plan

<Warning>
  The current beta build contains the collection-plan route, authentication UI, Configuration JSON field, schedule UI, and shared API contracts, but it does not provide the complete production save workflow. Profile creation and update and the production collection-job routes are still being implemented. Do not enter credentials or rely on the steps below until your SpecterOps account team confirms that the complete workflow is available in your tenant.
</Warning>

When the workflow is enabled, the beta form creates an AWS plan. The **Service** and **Authentication Type** fields are fixed because AWS and access-key authentication are the only beta options.

The planned beta workflow includes:

- Open **Administration** > **Data Collection** > **Managed Collection**, then select **New Collection**.
- Enter a plan **Name** and confirm that **Service** is **AWS**.
- In **Authentication**, confirm that **Authentication Type** is **Access Key**, then provide the **Access Key ID** and **Secret Access Key**. BloodHound Enterprise saves the credential separately and does not display the secret value again.
- In **Configuration**, paste the JSON object that defines the collection job. Use the linked [AWS collector documentation](/openhound/collectors/aws/collect-data#aws-organization-profile-recommended) for the supported schema, required fields, and examples. The field accepts a JSON object, not a TOML file, array, or scalar value. The form checks JSON syntax only; it does not confirm that the AWS settings are semantically valid or that the credential has the required permissions. Match the collection scope to the permissions in [Configure AWS permissions](/openhound/collectors/aws/configure-permissions).
- If you want automatic collection, enter a **Schedule Name**, confirm **Frequency** is **Daily**, and select a **Start Time**. The menu provides every hour from **12:00am** through **11:00pm** in one-hour increments. BloodHound Enterprise displays the selected time in your detected local timezone and shows the corresponding GMT offset; the schedule is stored as a UTC recurrence.
- Select **Save** after the collection-plan workflow is available. The plan should then appear on the **Collection Plans** page.

<Note>
  The Managed Collectors beta is still being rolled out. If the configuration, schedule, or save action is unavailable in your tenant, contact your SpecterOps account team. Do not create a self-deployed collector client as a substitute for this workflow.
</Note>

## Review collection plans

After the collection-plan workflow is available, the **Collection Plans** page displays each plan as a tile. A tile can show:

- The plan name.
- Its daily schedule, or **No schedule set** when it has no schedule.
- The latest run time, or **Not run yet** when the plan has not produced a completed run.
- The latest result: **Success**, **Failed**, or **Cancelled**.

The current edit page can display and locally edit plan details and the Configuration JSON field, but profile name and configuration updates are not yet wired to the production save workflow. Authentication settings remain immutable after a credential is saved. When profile updates are available, changes will apply to future jobs. A job that BloodHound Enterprise already created uses the configuration captured when that job was created.

The beta does not provide a separate test-connection action. A saved credential is used when a collection job executes, so **Not run yet** does not confirm that the credential or AWS permissions are valid. When the production queue route is available, select **Run** to queue an on-demand collection. The action does not itself indicate terminal completion; wait for the latest history result, then use [Troubleshoot managed collection](/collect-data/enterprise-collection/managed-collectors/troubleshoot) if it fails.

## Replace an AWS credential

Managed Collectors does not edit a saved secret in place. The current collection-job design treats secret deletion as a separate operation from plan deletion: deleting a plan removes its profile and schedule links but does not revoke the AWS key or automatically delete the secret reference. Do not use plan deletion alone as credential rotation.

When the complete workflow is available, create a new plan with the replacement access key pair, confirm that the new plan collects successfully, revoke the old AWS key according to your organization's credential policy, and follow the SpecterOps-provided process for removing the old secret reference.

<Warning>
  Never paste a secret access key into a ticket, log, screenshot, or support bundle. BloodHound Enterprise does not display the saved secret value after the credential is created.
</Warning>

<Warning>
  Keep credentials, BHE tokens, and other secret values out of **Configuration**. Enter only the non-secret JSON settings required by the collection job; authentication credentials are handled in the separate **Authentication** section.
</Warning>

## Delete a collection plan

Delete a plan when you no longer need it or when you have replaced its credentials. Deleting a plan does not revoke the AWS key or automatically delete its secret reference.

<Steps>
  <Step title="Open the plan actions">
    On **Collection Plans**, find the plan and select **Delete**.
  </Step>

  <Step title="Confirm deletion">
    Review the confirmation dialog and confirm the deletion. The plan is removed from the collection plan list and future scheduled jobs are no longer created from it. Linked schedule records survive profile deletion in the collector-job design.
  </Step>
</Steps>

Jobs that BloodHound Enterprise already created are independent snapshots. Deleting or editing the plan does not rewrite a job that is already queued or running. Revoking the credential used by a queued or running job can still cause that job to fail.

## Run a collection on demand

After the collection-plan workflow is available, on-demand collection is the quickest beta method for validating a saved AWS credential because the beta does not provide a separate test-connection action.

<Steps>
  <Step title="Queue the collection">
    On **Collection Plans**, find the plan and select **Run**. BloodHound Enterprise queues a job using the plan's saved credential and collection configuration.
  </Step>

  <Step title="Review the result">
    Review the plan's latest run and result. A failed run indicates that you should check the AWS credential, collection scope, and required permissions before you create a schedule.
  </Step>
</Steps>

If **Run** does not queue a job, record the plan name, time of the attempt, and visible error text, then contact your SpecterOps account team. Do not include credential values.
