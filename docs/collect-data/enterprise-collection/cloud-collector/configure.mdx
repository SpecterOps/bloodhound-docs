Use a collection plan to define cloud service credentials, collection scope, and an optional schedule for Cloud Collector.

After the beta is enabled in your tenant, create or edit a plan, use on-demand collection, and review its job history to confirm collection activity.

<Note>
  Cloud Collector job history is self-contained. These jobs do not appear on the **Administration** > **Manage Clients** or **Administration** > **Finished Jobs Log** pages.
</Note>

## Prerequisites

Before you configure a collection plan, confirm that the following prerequisites are met:

- Your BloodHound Enterprise tenant has Cloud Collector enabled by SpecterOps and your account has the Administrator role.
- You have an [AWS access key ID and secret access key](https://docs.aws.amazon.com/IAM/latest/UserGuide/access-keys-admin-managed.html) for a collection principal.
- You know your AWS Organizations management account ID and the names of the management and member-account collection roles.
- You have [configured AWS permissions](/collect-data/enterprise-collection/cloud-collector/security-and-compliance#configure-aws-permissions), including role trust and permission to assume the roles.
- You have chosen a [member-role path](#choose-a-member-role-path) that matches those trust relationships.

<Warning>
  The beta accepts an access key ID and secret access key for the starting AWS identity. It does not accept an initial STS session token or role-only authentication instead of that key pair. After authenticating, the collector uses AWS Security Token Service (STS) to assume the configured collection roles.

  Check your company's guidelines for granting this access before you configure a plan.
</Warning>

## AWS collection scope

The Cloud Collector beta surveys an AWS organization, discovers its active accounts, and builds the configuration used for collection. It reads AWS Organizations metadata through the management identity and collects resources from the management account and accessible active member accounts.

The beta supports both member-role paths below. It does not yet support single-account collection, independent-account collection, custom finished AWS configurations, or customer-provided AWS files and named profiles.

The survey uses one collection role name across member accounts. It does not select different role names or trust paths per member. All discovered active members are collection targets; missing roles or denied access can leave accounts uncollected.

## Choose a member-role path

Choose `member_role_source` according to the identity trusted by your member-account roles:

| Value | Management-account access | Member-account access |
| --- | --- | --- |
| `source` | The starting key identity assumes the management role. | The starting key identity directly assumes each member role. Member roles must trust that starting principal. |
| `management` | The starting key identity assumes the management role. | The management role assumes each member role. Member roles must trust that management role. |

The starting identity may belong to the management account or another account. This choice does not describe where Cloud Collector runs. Both paths require the caller's `sts:AssumeRole` permissions and the target role's trust policy. Follow [Configure AWS permissions](/collect-data/enterprise-collection/cloud-collector/security-and-compliance#configure-aws-permissions) to establish both.

## AWS configuration

Paste one of the following complete objects into the plan's **Configuration** field. Replace `111111111111` with your management account ID and replace the role names if yours differ. Choose the tab that matches your member-role trust.

<Tabs>
  <Tab title="Direct from source identity">
    Use this object when member roles trust the starting key identity:

    ```json
    {
      "sources": {
        "source": {
          "aws": {
            "credentials": {
              "management_account_id": "111111111111",
              "management_role_name": "OpenHoundManagementRole",
              "collector_assumed_role_name": "OpenHoundCollectorRole",
              "member_role_source": "source",
              "runtime_auth_mode": "default_chain"
            },
            "bucket_policy": {
              "include": false
            }
          }
        }
      }
    }
    ```
  </Tab>
  <Tab title="Through management identity">
    Use this object when member roles trust the management role:

    ```json
    {
      "sources": {
        "source": {
          "aws": {
            "credentials": {
              "management_account_id": "111111111111",
              "management_role_name": "OpenHoundManagementRole",
              "collector_assumed_role_name": "OpenHoundCollectorRole",
              "member_role_source": "management",
              "runtime_auth_mode": "default_chain"
            },
            "bucket_policy": {
              "include": false
            }
          }
        }
      }
    }
    ```
  </Tab>
</Tabs>

### AWS settings

The following settings belong inside `sources.source.aws.credentials`. Despite the section name, the examples contain only non-secret authentication settings, not the access key pair.

| Setting | Requirement and behavior |
| --- | --- |
| `management_account_id` | Required. The AWS Organizations management account ID; it is not discovered automatically. |
| `management_role_name` | Set explicitly as shown. The role the starting identity assumes for organization survey, Organizations data, and management-account resource collection. |
| `collector_assumed_role_name` | Required. The role assumed in every active member account. |
| `member_role_source` | Required. Use `source` or `management` according to the [member-role path](#choose-a-member-role-path). |
| `runtime_auth_mode` | Use `default_chain` as shown so the AWS SDK selects the key pair supplied by Cloud Collector. |
| `collector_assumed_role_session_name` | Optional. The STS role session name; defaults to `openhound-aws-collection`. |

<Warning>
  Set `management_role_name` explicitly even if the access key belongs to a user in the management account. If you omit it, the extension defaults the role name to `collector_assumed_role_name`, but uses a starting identity already in management without a role hop. That no-hop path cannot be represented using the environment credentials supplied by Cloud Collector. An explicit management role makes the collector assume that role instead.
</Warning>

Do not add self-hosted file/profile settings such as `aws_config_file`, `source_config_file`, `credentials_file`, or `collector_profile_name`, and do not enable `survey_only`. Cloud Collector supplies the collection credentials and handles the generated configuration.

### Optional S3 inventory

S3 bucket and object inventory is disabled by default. Account-level S3 public access block settings are collected independently of this switch. Object inventory contains names and metadata, not object contents.

To enable bucket and object inventory, use a complete configuration such as the following. This example uses the `source` member-role path.

```json
{
  "sources": {
    "source": {
      "aws": {
        "credentials": {
          "management_account_id": "111111111111",
          "management_role_name": "OpenHoundManagementRole",
          "collector_assumed_role_name": "OpenHoundCollectorRole",
          "member_role_source": "source",
          "runtime_auth_mode": "default_chain"
        },
        "bucket_policy": {
          "include": true,
          "max_objects": 10,
          "rule": [
            {
              "include": true,
              "match_bucket": "\\A[\\s\\S]*\\Z",
              "match_object": "\\A[\\s\\S]*\\Z"
            }
          ]
        }
      }
    }
  }
}
```

| Setting | Default | Behavior |
| --- | --- | --- |
| `include` | `false` | Enables bucket inventory. When enabled, bucket metadata is collected even for buckets excluded from object inventory by rules. |
| `max_objects` | `10` | Per-bucket limit on the object listing considered for collection. Set to `0` to skip objects while retaining bucket inventory. |
| `rule[].include` | `true` | Includes matching names unless an exclusion also matches. |
| `rule[].match_bucket` | None | Regular expression searched against the bucket name to select buckets for object inventory. |
| `rule[].match_object` | None | Regular expression searched against object keys to select object metadata. |

Bucket and object matching are independent: a bucket must match an inclusion in the bucket rules, and an object must match an inclusion in the object rules. Exclusions win in each set, regardless of rule order. A rule containing both expressions contributes to both sets; it is not a paired bucket-and-key condition.

Rules are applied locally, not as AWS permission boundaries. Object filtering occurs after the per-bucket listing limit, so fewer than `max_objects` matching objects may be stored. Enabling buckets without object inclusion rules collects bucket metadata but no objects.

## Configure a collection plan

A collection plan tells BloodHound Enterprise what to collect from your cloud environment and when. It combines your service credentials, collection scope, and an optional schedule. The form has three steps:

<Icon icon="square-1" iconType="solid" size={32}/> **Profile**
<Icon icon="square-2" iconType="solid" size={32}/> **Secret**
<Icon icon="square-3" iconType="solid" size={32}/> **Schedule**

In the left navigation menu, go to **Administration** > **Data Collection** > **Cloud Collector**. Select **New Collection** to create a plan or **Edit** on a plan tile to change one.

<Steps>
  <Step id="profile" title="Enter profile details and configuration">
    In the **Collection Plan** section, enter or update the collection plan **Name**.

    <Note>
      The **Service** field defaults to **AWS Collection** and cannot be changed.
    </Note>

    In the **Profile** section, replace the initial JSON object with an [AWS configuration example](#aws-configuration) from this page.

    Confirm that the management account ID, role names, and `member_role_source` match your AWS permissions.

    The field accepts a JSON object, not a TOML file, array, or scalar value. The form checks JSON syntax and that the value is an object; it does not confirm that the settings are semantically valid or that the credential has the required permissions.

    <Warning>
      Keep credentials, BloodHound Enterprise tokens, and other secret values out of **Configuration**. Enter only the non-secret JSON settings required by the collection job; authentication credentials are handled in the separate **Secrets** step.
    </Warning>

    <Frame>
      <img src="/images/data_collectors/cloud-collector/collection-plan-profile.png" alt="Profile section in the Cloud Collector plan form" />
    </Frame>

    <Tip>
      Click **Format JSON** below the JSON input field to automatically format the JSON object for readability.
    </Tip>

    Click **Next** to proceed to the **Secret** step.
  </Step>

  <Step id="credential" title="Add or select a credential">
    In the **Secrets** section, select **New Credentials** or **Existing Credentials**.

    For a new credential, enter a **Secret Name**, **Access Key ID**, and **Secret Access Key**. The **Authentication Type** is **Access Key**. For an existing credential, select it by its saved name.

    When you edit a plan, you can only select an existing credential. To use a new key pair, first create the credential in [Manage credentials](#manage-credentials), then select it in the plan.

    <Note>
      BloodHound Enterprise does not display a saved secret access key again. To change a saved credential, see [Manage credentials](#manage-credentials).
    </Note>

    Your credentials are encrypted and stored securely.

    <Frame>
      <img src="/images/data_collectors/cloud-collector/collection-plan-secret.png" alt="Secret section in the Cloud Collector plan form" />
    </Frame>

    Click **Next** to proceed to the **Schedule** step.
  </Step>

  <Step id="schedule" title="Configure a schedule">
    In the **Schedule** section, choose whether to use a new schedule, a schedule saved for another plan, or no schedule. A plan without a schedule can still run on demand.

    For a new schedule, enter a **Schedule Name** and select a **Start Time**. For an existing schedule, select it by name.

    <Note>
      The **Frequency** field defaults to **Daily** and cannot be changed.
    </Note>

    The **Start Time** menu provides every hour from **12:00am** through **11:00pm** in one-hour increments.

    BloodHound Enterprise displays the selected time in your detected local timezone and shows the corresponding GMT offset. The schedule is stored as a UTC recurrence.

    <Frame>
      <img src="/images/data_collectors/cloud-collector/collection-plan-schedule.png" alt="Schedule section in the Cloud Collector plan form" />
    </Frame>

    Click **Create Plan** to complete collection plan configuration.

    BloodHound Enterprise validates the form, saves the plan and any new credential or schedule, and displays a success notification. The plan appears on the **Collection Plans** page.
  </Step>
</Steps>

## Run a collection on demand

On-demand collection is the quickest method for validating a saved credential because the beta does not provide a separate test-connection action.

<Steps>
  <Step title="Queue the collection">
    On the **Collection Plans** page, find the plan tile and click **Run**.
    
    BloodHound Enterprise queues a job using the plan's saved credential and collection configuration.
  </Step>

  <Step title="Review the result">
    Review the plan's latest run and result in the tile or **History**.

    A **Failed** or **Warning** result indicates that you should check the credential, role trust, and required permissions before relying on scheduled collection. A **Success** result does not prove that every account and resource was readable; review unexpected gaps with your SpecterOps account team.

    If **Run** does not queue a job, record the plan name, time of the attempt, and visible error text, and contact your SpecterOps account team. Do not include credential values.
  </Step>
</Steps>

## Review collection plans

After you save a plan, the **Collection Plans** page displays it as a tile.

<Frame>
  <img src="/images/data_collectors/cloud-collector/collection-plan-home.png" alt="Collection plan tile on the Collection Plans page" />

A tile can show:

| Tile field | What it shows |
| --- | --- |
| Plan name | The name of the collection plan |
| Schedule | The schedule, with **Disabled** when paused, or **No schedule set** when the plan has no schedule |
| Latest run time | The latest run time (or **Not run yet** when the plan has not produced a completed run) |
| Latest result | **Success**, **Warning** (partial success), **Failed**, or **Cancelled**. Open **History** for a failure reason. |

Click **History** on a plan tile to open its **Job History** drawer. The **Job History** drawer shows:

| Column | Description |
| --- | --- |
| **Job ID** | The unique identifier for the job. |
| **Started at** | The time the job started. |
| **Completed at** | The time the job completed. |
| **Run Result** | The outcome of the job. |

Use the **Run Results** filter, sort the **Started at** or **Completed at** columns, and hover a **Failed** or **Warning** result to view its failure reason.

<Note>

## Manage credentials

Use the **Manage Credentials** drawer to view saved credentials and the collection plans that use them, and to create, edit, or delete credentials.

On the **Collection Plans** page, click the key icon (**Manage Credentials**) to open the drawer. The credentials table shows:

| Column | Description |
| --- | --- |
| **Credential Name** | The saved name of the credential. |
| **Access Key ID** | The AWS access key ID. |
| **Created** | The date the credential was created. |
| **Plans** | The number of collection plans that use the credential, or **Unused** when no plan uses it. |
| **Actions** | Edit and delete actions for the credential. |

Enter a name in **Search credentials by name** to filter the table.

<Note>
  Users without permission to manage collection plans can view the table, but they do not see **Create Credential** or the **Actions** column.
</Note>

### Create a credential

Create a credential before you need it in a plan, for example to rotate a key pair.

<Steps>
  <Step title="Open the dialog">
    In the **Manage Credentials** drawer, click **Create Credential**.
  </Step>

  <Step title="Enter the key pair">
    Enter a **Secret Name**, **Access Key ID**, and **Secret Access Key**. The **Authentication Type** is **Access Key**.

    Credential names must be unique.
  </Step>

  <Step title="Save the credential">
    Click **Create Credential**. The credential appears in the table as **Unused** until you select it in a collection plan.
  </Step>
</Steps>

### Edit a credential

<Steps>
  <Step title="Open the dialog">
    In the credentials table, click the edit icon for the credential.

    The **Edit Credential** dialog lists the collection plans that use the credential.
  </Step>

  <Step title="Update the credential">
    Update the **Secret Name** or **Access Key ID**. To replace the secret access key, click **Replace** and enter the new **Secret Access Key**. Click **Keep existing** to cancel the replacement.
  </Step>

  <Step title="Save your changes">
    Click **Save**.

    Changes apply to every collection plan that uses the credential.
  </Step>
</Steps>

### Delete a credential

Deleting a credential permanently deletes it and removes its association with every collection plan that uses it. Those plans cannot collect successfully until you edit each one and select another existing credential.

<Steps>
  <Step title="Open the dialog">
    In the credentials table, click the delete icon for the credential.

    The dialog lists any affected collection plans.
  </Step>

  <Step title="Confirm deletion">
    Type the credential name to confirm, then click **Delete Credential**.
  </Step>
</Steps>

<Note>
  Deleting a credential does not revoke the AWS access key. Revoke the key in AWS according to your organization's credential policy.
</Note>

## Rotate a credential

To rotate a credential, update the saved credential or switch your plans to a new one:

- **Update the saved credential:** [edit the credential](#edit-a-credential), enter the new **Access Key ID**, and replace the **Secret Access Key**. Every plan that uses the credential uses the new key pair.
- **Switch to a new credential:** [create a credential](#create-a-credential) with the new key pair, then edit each plan and select it in the **Secrets** step. When no plan uses the old credential, [delete it](#delete-a-credential).

Run a collection on demand to validate the new key pair, then revoke the old AWS key according to your organization's credential policy.

Cloud Collector jobs keep the access key ID that they captured when BloodHound Enterprise created them. A job that is already queued or running when you change or revoke the key can fail.

## Delete a collection plan

Delete a collection plan when you no longer need it.

Cloud Collector jobs that BloodHound Enterprise created before the plan's deletion are independent snapshots. Deleting or editing the plan does not rewrite a job that is already queued or running.

<Note>
  Deleting a plan does not revoke the AWS key or delete its credential. To delete a credential that no plan uses, see [Delete a credential](#delete-a-credential).
</Note>

<Steps>
  <Step title="Open the plan actions">
    On the **Collection Plans** page, find the plan and click **Delete**.
  </Step>

  <Step title="Confirm deletion">
    Review the confirmation dialog and confirm the deletion.

    The plan is removed from the collection plan list and future scheduled jobs are no longer created from it.
  </Step>
</Steps>
