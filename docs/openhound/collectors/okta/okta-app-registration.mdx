<img noZoom src="/assets/enterprise-AND-community-edition-pill-tag.svg" alt="Applies to BloodHound Enterprise and CE"/>

The OpenHound Okta collector authenticates to the Okta API using an OAuth 2.0 service application with a public/private key pair.

To create the Okta application registration for the OpenHound Okta collector, follow the steps below.

Use an administrator who can create service apps and assign the required admin roles. A Super Administrator must grant the Okta API scopes. The application is the runtime collection identity; the administrator does not need to maintain an interactive session during collection. See [Okta's service app setup](https://developer.okta.com/docs/guides/implement-oauth-for-okta-serviceapp/main/) for prerequisites and console variations.

<Steps>
  <Step title="Open the Applications page">
    In the Okta Admin Console, open **Applications and Resources > Applications** and select **Create App Integration**. Older console layouts use **Applications > Applications**. If prompted, select **Classic experience**.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration1.png" alt="Okta Admin Console - Applications page" />
    </Frame>
  </Step>

  <Step title="Select API Services">
    In the **Create a new app integration** dialog, select **API Services** and click **Next**.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration2.png" alt="Create a new app integration - select API Services" />
    </Frame>
  </Step>

  <Step title="Name the application">
    Enter a name for the app integration and click **Save**.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration3.png" alt="New API Services App Integration - name" />
    </Frame>
  </Step>

  <Step title="Configure public key authentication">
    After the application is created, you are taken to the **General** tab. Make a note of the newly created application's Client ID for the collector.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration4.png" alt="OpenHound app - Client Credentials" />
    </Frame>

    Under **Client Credentials**, click **Edit** and change **Client authentication** from **Client secret** to **Public key / Private key**.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration5.png" alt="Switch to Public key / Private key authentication" />
    </Frame>
  </Step>

  <Step title="Generate a key pair">
    Under **PUBLIC KEYS**, click **Add key**, then click **Generate new key**.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration6.png" alt="Add a public key dialog" />
    </Frame>

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration7.png" alt="Generated key pair - copy the private key" />
    </Frame>

    <Warning>Copy the private key (JSON) and store it securely — it is only displayed once.</Warning>

    Click **Done** to close the key dialog.
  </Step>

  <Step title="Save the credentials">
    Verify the key appears in the **PUBLIC KEYS** table, then click **Save**.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration8.png" alt="Public key listed in credentials" />
    </Frame>

    Confirm the prompt that existing client secrets will no longer be used.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration9.png" alt="Confirm client secret removal" />
    </Frame>
  </Step>

  <Step title="Disable DPoP requirement">
    Uncheck the **Require Demonstrating of Proof of Possession (DPoP)** option and click **Save**.

    <Frame>
      <img src="/images/extensions/okta/okta-app-registration/app-registration10.png" alt="App General Settings" />
    </Frame>
  </Step>

  <Step title="Grant OAuth 2.0 scopes">
    Navigate to the **Okta API Scopes** tab and grant the scopes required by the OpenHound Okta collector.

    The Okta application registration used by the OpenHound Okta collector requires the following [OAuth 2.0 scopes](https://developer.okta.com/docs/api/oauth2/) for data collection to function correctly:

    | OAuth 2.0 Scope | Description |
    |-----------------|-------------|
    | `okta.agentPools.read` | Allows the app to read agent pools in your Okta organization. |
    | `okta.apiTokens.read` | Allows the app to read API tokens in your Okta organization. |
    | `okta.appGrants.read` | Allows the app to read grants in your Okta organization. |
    | [okta.apps.read](https://developer.okta.com/docs/api/openapi/okta-management/guides/permissions/#oktaappsread) | Allows the app to read information about Apps in your Okta organization. |
    | `okta.authenticators.read` | Allows the app to read authenticators in your Okta organization. |
    | `okta.authorizationServers.read` | Allows the app to read information about authorization servers in your Okta organization. |
    | `okta.clients.read` | Allows the app to read OAuth 2.0 clients in your Okta organization. |
    | [okta.devices.read](https://developer.okta.com/docs/api/openapi/okta-management/guides/permissions/#oktadevicesread) | Allows the app to read the existing device's profile and search devices. |
    | `okta.features.read` | Allows the app to read information about features in your Okta organization. |
    | [okta.groups.read](https://developer.okta.com/docs/api/openapi/okta-management/guides/permissions/#oktagroupsread) | Allows the app to read information about groups and their members in your Okta organization. |
    | `okta.idps.read` | Allows the app to read information about identity providers in your Okta organization. |
    | `okta.oauthIntegrations.read` | Allows the app to read API service integration instances in your Okta organization. |
    | `okta.orgs.read` | Allows the app to read organization-specific details about your Okta organization. |
    | [okta.policies.read](https://developer.okta.com/docs/api/openapi/okta-management/guides/permissions/#oktapoliciesread) | Allows the app to read information about policies in your Okta organization. |
    | `okta.realmAssignments.read` | Allows the app to read realm assignments in your Okta organization. |
    | [okta.realms.read](https://developer.okta.com/docs/api/openapi/okta-management/guides/permissions/#oktarealmsread) | Allows the app to read the existing realms and their details. |
    | `okta.roles.read` | Allows the app to read administrative role assignments for users in your Okta organization. |
    | [okta.users.read](https://developer.okta.com/docs/api/openapi/okta-management/guides/permissions/#oktausersread) | Allows the app to read the existing users' profiles and credentials. |

    <Note>
    The [`okta.realms.read`](https://developer.okta.com/docs/api/openapi/okta-management/management/tag/Realm) and [`okta.realmAssignments.read`](https://developer.okta.com/docs/api/openapi/okta-management/management/tag/RealmAssignment) scopes are optional and requires Okta Identity Governance or Secure Partner Access.
    </Note>

    </Step>

  <Step title="Assign admin roles">
    In addition to the OAuth 2.0 scopes granted above, the application must also be assigned Okta admin roles.
    Navigate to the **Admin roles** tab and assign one of the following role combinations:

    <Tabs>
      <Tab title="Full data collection">
        Assign the [**Super Administrator**](https://help.okta.com/en-us/content/topics/security/administrators-super-admin.htm) role to the application.

        <Note>
        The Super Administrator role is currently the only Okta admin role that allows reading application OAuth 2.0 grants and API service integrations,
        as the permissions corresponding to the `okta.appGrants.read` and `okta.oauthIntegrations.read` scopes cannot be delegated to custom admin roles.
        The app's effective API access depends on both its admin role and the scopes in its token. These read scopes constrain collection, but the Super Administrator assignment remains privileged. Protect the private key, review all grants, and avoid adding write scopes to the collection identity.
        </Note>
      </Tab>

      <Tab title="Reduced access">
        If assigning the Super Administrator role is not acceptable in your environment, a less privileged combination of roles can be used instead,
        at the cost of the collector not being able to read application OAuth 2.0 grants and API service integrations.

        1. Assign the [**Read-only Administrator**](https://help.okta.com/en-us/content/topics/security/administrators-read-only-admin.htm) role to the application.

        2. As the Read-only Administrator role does not allow reading admin role assignments, create a [custom admin role](https://help.okta.com/en-us/content/topics/security/custom-admin-role/about-creating-custom-admin-roles.htm) called **IAM Readers** with the **View roles, resources, and admin assignments** permission.

           <Frame>
             <img src="/images/extensions/okta/okta-app-registration/okta-custom-role-iam-readers-permissions.png" alt="Custom admin role IAM Readers with the View roles, resources, and admin assignments permission" />
           </Frame>

        3. Create a [resource set](https://help.okta.com/oie/en-us/content/topics/security/custom-admin-role/create-resource-set.htm) called **IAM Resources** containing **All Identity and Access Management resources**.

           <Frame>
             <img src="/images/extensions/okta/okta-app-registration/okta-custom-resource-set-iam-resources.png" alt="Resource set IAM Resources containing all Identity and Access Management resources" />
           </Frame>

        4. Assign the **IAM Readers** role to the application, scoped to the **IAM Resources** resource set.

           <Frame>
              <img src="/images/extensions/okta/okta-app-registration/okta-custom-role-iam-readers-assignment.png" alt="IAM Readers role assigned to the OpenHound application, scoped to the IAM Resources resource set" />
           </Frame>

        <Warning>
        The permissions corresponding to the `okta.appGrants.read` and `okta.oauthIntegrations.read` scopes cannot be delegated to custom admin roles.
        With this role combination, the collector therefore cannot read application OAuth 2.0 grants or enumerate API service integrations.
        As a consequence, the `oauth_scopes` property of [Okta_Application](/opengraph/extensions/okta/nodes/okta_application) nodes will not be populated,
        and [Okta_APIServiceIntegration](/opengraph/extensions/okta/nodes/okta_apiserviceintegration) nodes will be missing from the graph entirely.
        Because an application's role permissions are filtered by its granted OAuth 2.0 scopes,
        attack path edges originating from OIDC applications will be missing from the graph as well.
        </Warning>
      </Tab>
    </Tabs>
  </Step>
</Steps>

## Verify access and maintain credentials

Before collecting, confirm the intended app's Client ID, registered public key, scope grants, and admin role assignments. Keep the private JWK's `kid` when saving the JSON. The collector requests the scopes listed above for every OAuth token, including the realm scopes; the optional license designation does not make the collector omit those scopes automatically. An `invalid_scope` response requires checking the requested scopes against the app grants and tenant capabilities.

These role profiles describe expected coverage, rather than a lab-verified least-privilege configuration. Verify the required datasets using the [collection coverage checks](/openhound/collectors/okta/collect-data#verify-collection-coverage).

For rotation, register a replacement public key and update the collector's private key together. Verify collection with the new key before retiring the old key. Only a Super Administrator can rotate a service app's keys after Okta-scoped grants are assigned; see [Okta's key-management requirements](https://developer.okta.com/docs/guides/implement-oauth-for-okta-serviceapp/main/).

## API token alternative

An SSWS token inherits its issuing administrator's privileges. OAuth scope grants do not restrict it. Use a dedicated account and an approved network restriction; a Super Administrator token can modify the organization. See [Okta's API token guide](https://developer.okta.com/docs/guides/create-an-api-token/main/).

<Steps>
  <Step title="Create the collection account">
    Create or select a dedicated Okta administrator account with the required resource access. Use Super Administrator only when full collection requires it; a narrower role can leave datasets unavailable.
  </Step>
  <Step title="Create and save the token">
    Sign in as that account. In **Security > API > Tokens**, select **Create token**, give it a collection-specific name, and configure permitted network origins. Copy the token once to your secret store.
  </Step>
  <Step title="Configure the collector">
    Set `base_url` and `token` using the [SSWS configuration example](/openhound/collectors/okta/collect-data#option-3-api-token-ssws), then verify dataset coverage. Do not configure private-key credentials at the same time.
  </Step>
</Steps>

SSWS tokens expire after 30 days without use and are deprovisioned when their owner is deactivated. For rotation, create a replacement, update the collector's secret, verify collection, then revoke the old token.
