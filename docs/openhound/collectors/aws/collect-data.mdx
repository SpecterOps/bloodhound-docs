This page covers configuring the OpenHound AWS collector for an AWS account or organization. Use this page to choose a collection strategy and configure the collector settings in the `secrets.toml` file or with environment variables.

## Prerequisites

Before you configure the AWS collector, ensure that the following prerequisites are met:

- [Collector client](/collect-data/enterprise-collection/create-collector) created in BloodHound Enterprise.
- AWS collector permissions [configured](/openhound/collectors/aws/configure-permissions) for the target AWS account or organization.

## Configure OpenHound

The AWS collector needs different settings based on the collection strategy you choose. You can set these values in one of two places:

| Method | Set the values here |
| --- | --- |
| `secrets.toml` file | `[sources.source.aws.credentials]` section |
| Environment variables | `SOURCES__SOURCE__AWS__CREDENTIALS` prefix |

<Warning>
  The beta must use the `openhound-aws` container image from the private ECR repository described in the [deployment examples](/openhound/collectors/aws/collect-data#deployment-examples). The public `openhound` image does not support AWS collection.
</Warning>

## Choose an account collection strategy

The collector supports three strategies:

- **AWS organization profile** <Badge color="green">Recommended</Badge>: Collect AWS organization metadata and fan out collection across member accounts.
- **Single AWS profile**: Collect resources from one AWS account.
- **Multiple AWS profiles**: Collect resources from multiple independent AWS accounts.

<Tip>
  **AWS organization profile** is the recommended collection strategy.
</Tip>

Click the tab that matches the strategy of the AWS scope you want to collect.

<Tabs>
  <Tab title="AWS organization profile (recommended)" icon="star">
    Use an organization profile to enumerate over all member accounts via the AWS management account.

    This assumes the configured IAM role in each member account. Also used to collect the organization structure, SCPs and RCPs.

    | Setting | Required | Default | Description |
    | --- | --- | --- | --- |
    | `profile_name` | Yes | None | Name of the AWS SDK profile used for collection. |
    | `org_role_name` | Yes | - | Name of the IAM role to assume in each active member account. The collector constructs `arn:aws:iam::<account-id>:role/<org_role_name>`. |
    | `org_role_session_name` | No | openhound-aws-org-collector | STS role session name used when assuming the member-account role.          |
    | `include_management_account` | No | false | Whether to collect account resources from the management account in addition to organization metadata and policies.  |

    **`secrets.toml`**

    ```toml title="~/.dlt/secrets.toml"
    [sources.source.aws.credentials]
    profile_name = "my_organization"
    org_role_name = "OpenHoundCollectorRole"
    org_role_session_name = "optional_session_name"
    include_management_account = true
    ```

    **Environment variables**

    ```bash
    SOURCES__SOURCE__AWS__CREDENTIALS__PROFILE_NAME="my_organization"
    SOURCES__SOURCE__AWS__CREDENTIALS__ORG_ROLE_NAME="OpenHoundCollectorRole"
    SOURCES__SOURCE__AWS__CREDENTIALS__ORG_ROLE_SESSION_NAME="optional_session_name"
    SOURCES__SOURCE__AWS__CREDENTIALS__INCLUDE_MANAGEMENT_ACCOUNT=true
    ```
  </Tab>
  <Tab title="Single AWS profile">
    Use a single named AWS profile to collect resources from one AWS account.

    | Setting | Required | Default | Description |
    | --- | --- | --- | --- |
    | `profile_name` | Yes | None | Name of the AWS SDK profile used for collection. |

    **`secrets.toml`**

    ```toml title="~/.dlt/secrets.toml"
    [sources.source.aws.credentials]
    profile_name = "production"
    ```

    **Environment variables**

    ```bash
    SOURCES__SOURCE__AWS__CREDENTIALS__PROFILE_NAME=production
    ```
  </Tab>
  <Tab title="Multiple AWS profiles">
    Use multiple named AWS profiles to collect resources from multiple independent AWS accounts.

    | Setting | Required | Default | Description |
    | --- | --- | --- | --- |
    | `profile_names` | Yes | None | Names of the AWS SDK profiles used for collection. |

    **`secrets.toml`**

    ```toml title="~/.dlt/secrets.toml"
    [sources.source.aws.credentials]
    profile_names = ["production", "testing"]
    ```

    **Environment variables**

    ```bash
    SOURCES__SOURCE__AWS__CREDENTIALS__PROFILE_NAMES='["production","testing"]'
    ```
  </Tab>
</Tabs>

## Configure S3 collection

S3 bucket collection is disabled by default. Enable it with the `bucket_policy.include` setting, then define bucket and object rules to control which S3 objects the collector stores for processing.

| Setting | Required | Default | Description |
| --- | --- | --- | --- |
| `include` | No | `false` | Enables S3 bucket collection. |
| `max_objects` | No | `10` | Maximum number of objects to collect from each included bucket. Set to `0` to skip object collection. |
| `rule.include` | No | `true` | Includes or excludes matching buckets or objects. Exclusion rules take precedence. |
| `rule.match_bucket` | No | None | Regular expression matched against the S3 bucket name. |
| `rule.match_object` | No | None | Regular expression matched against the S3 object key. |

Buckets and objects are excluded from object collection by default. A bucket or object must match at least one rule where `include` is `true`. If a bucket or object also matches a rule where `include` is `false`, the exclusion wins.

```toml
[sources.source.aws.bucket_policy]
include = true
max_objects = 100

[[sources.source.aws.bucket_policy.rule]]
include = true
match_bucket = "^production.*$"

[[sources.source.aws.bucket_policy.rule]]
include = false
match_bucket = ".*logs.*"

[[sources.source.aws.bucket_policy.rule]]
include = true
match_object = "\\.(json|csv)$"

[[sources.source.aws.bucket_policy.rule]]
include = false
match_object = ".*secret.*"
```

<Note>
  Bucket and object filters apply after AWS API responses are returned. Excluded buckets or objects can still appear in API responses, but the collector does not store excluded objects for further processing.
</Note>

## Configuration examples

The following examples show how to configure the AWS collector for different collection strategies. Replace placeholder values with your own.

### Single account collection without buckets

```toml 
[destination.bloodhoundenterprise]
token_key = "<BHE_TOKEN_KEY>"
token_id = "<BHE_TOKEN_ID>"
url = "https://your-tenant.bhe.io"

[sources.source.aws.credentials]
profile_name = "<AWS_PROFILE_NAME>"

[sources.source.aws.bucket_policy]
include = false
max_objects = 0
```

### Single account collection for all buckets

```toml
[destination.bloodhoundenterprise]
token_key = "<BHE_TOKEN_KEY>"
token_id = "<BHE_TOKEN_ID>"
url = "https://your-tenant.bhe.io"

[sources.source.aws.credentials]
profile_name = "<AWS_PROFILE_NAME>"

[sources.source.aws.bucket_policy]
include = true
max_objects = 50

[[sources.source.aws.bucket_policy.rule]]
include = true
match_bucket = ".*"

[[sources.source.aws.bucket_policy.rule]]
include = true
match_object = ".*"
```

### Multi-account collection without buckets

```toml
[destination.bloodhoundenterprise]
token_key = "<BHE_TOKEN_KEY>"
token_id = "<BHE_TOKEN_ID>"
url = "https://your-tenant.bhe.io"

[sources.source.aws.credentials]
profile_names = [
  "<AWS_PROFILE_NAME_1>",
  "<AWS_PROFILE_NAME_2>",
  "<AWS_PROFILE_NAME_3>"
]

[sources.source.aws.bucket_policy]
include = false
max_objects = 0
```

### Organization-wide collection without buckets

```toml
[destination.bloodhoundenterprise]
token_key = "<BHE_TOKEN_KEY>"
token_id = "<BHE_TOKEN_ID>"
url = "https://your-tenant.bhe.io"

[sources.source.aws.credentials]
profile_name = "<AWS_MANAGEMENT_PROFILE_NAME>"
org_role_name = "OpenHoundCollectorRole"
org_role_session_name = "OpenHoundCollectorSession"
include_management_account = true

[sources.source.aws.bucket_policy]
include = false
max_objects = 0
```

## Deployment examples

Before deploying, ensure that a valid `secrets.toml` file is available. It must contain the BloodHound Enterprise credentials, AWS target profile(s), and optionally bucket collection policies. The deployment method determines how this file is provided to the collector.

### Docker Compose

The Docker Compose example assumes that the secrets file is stored in the user's home directory at `~/.dlt/secrets.toml`.

The `openhound-aws` container image is available from the following private ECR repository:

```text
ec-e7d32cd970094ca9839c97a7c4abb4d2.ecs.us-east-2.on.aws
```

<Note>
  The password to the private container repository will be provided by SpecterOps.
</Note>

<Steps>
  <Step title="Log in to the private repository">
    Configure the Docker CLI to authenticate to the private repository. When prompted for the password, enter the SpecterOps-provided repository password.

    ```bash
    docker login --username ecr-proxy ec-e7d32cd970094ca9839c97a7c4abb4d2.ecs.us-east-2.on.aws
    ```
  </Step>

  <Step title="Pull the OpenHound AWS image">
    Test that you can pull the `openhound-aws` image. You can replace `docker` with `podman` if needed.

    ```bash
    docker pull ec-e7d32cd970094ca9839c97a7c4abb4d2.ecs.us-east-2.on.aws/openhound/openhound-aws:main
    ```
  </Step>

  <Step title="Create the Docker Compose file">
    Save the following Compose template as a `docker-compose.yaml` file, then run `docker compose up` to start the collector.

    ```yaml title="docker-compose.yaml"
    x-scheduler: &scheduler
      image: ec-e7d32cd970094ca9839c97a7c4abb4d2.ecs.us-east-2.on.aws/openhound/openhound-aws:main
      restart: unless-stopped
      init: true

      environment: &env
        LOG_LEVEL: INFO
        EXTRACT__WORKERS: 8
        LOG_CONTAINER: true

    services:
      scheduler-aws:
        <<: *scheduler
        environment:
          <<: *env
          DESTINATION__BLOODHOUNDENTERPRISE__COLLECTOR_NAME: aws
          AWS_CONFIG_FILE: /app/.aws/config
          AWS_SHARED_CREDENTIALS_FILE: /app/.aws/credentials

        secrets:
          - source: secrets_aws
            target: /app/.dlt/secrets.toml

          - source: config_aws
            target: /app/.aws/config

          - source: credentials_aws
            target: /app/.aws/credentials

    secrets:
      secrets_aws:
        file: ${HOME}/.dlt/secrets.toml

      config_aws:
        file: ${HOME}/.aws/config

      credentials_aws:
        file: ${HOME}/.aws/credentials
    ```
  </Step>
</Steps>

### Kubernetes

You can deploy the AWS collector with the example [OpenHound Helm chart](https://github.com/SpecterOps/OpenHound/tree/main/deployments/helm/openhound). This example uses the beta `openhound-aws` image from the private registry and assumes that the Kubernetes namespace is `openhound`.

Before you install the chart, create the following resources in the same namespace as the Helm release:

- A registry pull secret named `regcred` containing credentials for the private registry.

  <Note>
    The password to the private registry will be provided by SpecterOps.
  </Note>

- An `openhound-aws-config` ConfigMap containing `config.toml`.
- An `openhound-aws-secrets` Secret containing `secrets.toml`.
- `aws-sdk-config` and `aws-sdk-credentials` Secrets containing the AWS SDK `config` and `credentials` files.

<Warning>
  Kubernetes Secrets contain sensitive data. Protect the local `secrets.toml` and AWS SDK files, and use a secrets-management workflow appropriate for your environment.
</Warning>

<Steps>
  <Step title="Create the Kubernetes configuration">
    If the namespace does not already exist, create it before creating the configuration resources:

    ```bash
    kubectl create namespace openhound
    ```

    Create a `config.toml` file with the non-sensitive runtime settings. The following example increases collection parallelism and explicitly disables S3 collection:

    ```toml title="config.toml"
    [extract]
    workers = 32
    max_parallel_items = 80

    [sources.source.aws.bucket_policy]
    include = false
    max_objects = 0
    ```

    Create the ConfigMap and the Secret that contains the AWS collector and BloodHound Enterprise settings:

    ```bash
    kubectl create configmap openhound-aws-config \
      --namespace openhound \
      --from-file=config.toml=./config.toml

    kubectl create secret generic openhound-aws-secrets \
      --namespace openhound \
      --from-file=secrets.toml=./secrets.toml
    ```

    For organization-wide collection, use the organization profile settings described in [AWS organization profile](#aws-organization-profile-recommended). For example:

    ```toml title="secrets.toml"
    [sources.source.aws.credentials]
    profile_name = "<AWS_MANAGEMENT_PROFILE_NAME>"
    region_name = "eu-north-1"
    org_role_name = "<AWS_ORGANIZATION_ROLE_NAME>"
    org_role_session_name = "<AWS_ORGANIZATION_ROLE_SESSION_NAME>"
    include_management_account = true

    [destination.bloodhoundenterprise]
    token_key = "<BHE_TOKEN_KEY>"
    token_id = "<BHE_TOKEN_ID>"
    url = "https://your-tenant.bhe.io"
    ```

    <Note>
      Use the AWS profile names and IAM role settings that match your collection strategy. Keep the BloodHound Enterprise token values in `secrets.toml`; do not commit this file to source control.
    </Note>
  </Step>

  <Step title="Mount the AWS SDK files">
    Create Secrets from the AWS SDK files that the collector will use. The key names must match the `secretKey` values in `values.yaml`:

    ```bash
    kubectl create secret generic aws-sdk-config \
      --namespace openhound \
      --from-file=config=<your_user_dir>/.aws/config

    kubectl create secret generic aws-sdk-credentials \
      --namespace openhound \
      --from-file=credentials=<your_user_dir>/.aws/credentials
    ```
  </Step>

  <Step title="Create the registry pull secret">
    Create a dedicated Docker configuration directory for the private collector registry credential. Do not use your normal Docker configuration file, which may contain credentials for multiple registries.

    If Docker uses `credsStore` or `credHelpers`, do not copy that configuration file directly. Export a registry-specific file with inline authentication, or create the Secret from the registry credentials supplied by your secrets manager. Do not commit the file to source control.

    Before creating `regcred`, confirm that the dedicated configuration file contains an `auths` entry for `ec-e7d32cd970094ca9839c97a7c4abb4d2.ecs.us-east-2.on.aws`.

    ```bash
    docker --config <path_to_docker_config_dir> login \
      --username=ecr-proxy \
      ec-e7d32cd970094ca9839c97a7c4abb4d2.ecs.us-east-2.on.aws

    kubectl create secret generic regcred \
      --namespace openhound \
      --from-file=.dockerconfigjson=<path_to_docker_config_dir>/config.json \
      --type=kubernetes.io/dockerconfigjson
    ```

    <Note>
      See Docker's documentation for [stdin authentication](https://docs.docker.com/reference/cli/docker/login/#password-stdin) and Kubernetes' documentation for [creating a pull Secret from an existing credentials file](https://kubernetes.io/docs/tasks/configure-pod-container/pull-image-private-registry/).
    </Note>
  </Step>

  <Step title="Create the Helm values file">
    Save the following as `values.yaml`. Replace any placeholder configuration values with values for your environment.

    ```yaml title="values.yaml"
    image:
      repository: ec-e7d32cd970094ca9839c97a7c4abb4d2.ecs.us-east-2.on.aws/openhound/openhound-aws
      tag: "latest"

    imagePullSecrets:
      - name: regcred

    env:
      AWS_CONFIG_FILE: /app/aws/config
      AWS_SHARED_CREDENTIALS_FILE: /app/aws/credentials
      LOG_CONTAINER: "true"
      RUNTIME__LOG_LEVEL: "INFO"

    config:
      existingConfigMap: openhound-aws-config
      existingSecret: openhound-aws-secrets

    collector:
      name: aws
      extraSecretMounts:
        sdk-credentials:
          secretName: aws-sdk-credentials
          secretKey: credentials
          mountPath: /app/aws/credentials
        sdk-config:
          secretName: aws-sdk-config
          secretKey: config
          mountPath: /app/aws/config
    ```
  </Step>

  <Step title="Install and verify the chart">
    Install the chart from the OpenHound repository:

    ```bash
    helm install openhound-aws \
      --namespace openhound \
      --create-namespace \
      --values values.yaml \
      <openhound_path>/deployments/helm/openhound
    ```

    Verify that the collector pod starts and review its logs:

    ```bash
    kubectl get pods --namespace openhound
    kubectl logs --namespace openhound -l app.kubernetes.io/name=openhound -f
    ```
  </Step>

  <Step title="Enable S3 collection (optional)">
    To enable S3 collection, update `config.toml` before creating or updating the ConfigMap. For example:

    ```toml title="config.toml"
    [sources.source.aws.bucket_policy]
    include = true
    max_objects = 10

    [[sources.source.aws.bucket_policy.rule]]
    include = true
    match_bucket = ".*"

    [[sources.source.aws.bucket_policy.rule]]
    include = true
    match_object = ".*"
    ```

    After changing the file, update the ConfigMap and restart the deployment so the pod reads the new configuration:

    ```bash
    kubectl create configmap openhound-aws-config \
      --namespace openhound \
      --from-file=config.toml=./config.toml \
      --dry-run=client \
      --output yaml | kubectl apply --filename -

    kubectl rollout restart deployment/openhound-aws --namespace openhound
    ```
  </Step>
</Steps>
