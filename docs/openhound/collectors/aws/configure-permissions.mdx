<AwsBetaNote />

This page explains how to grant the OpenHound AWS collector the read-only AWS permissions it needs for single-account, multiple independent-account, or organization collection.

## Choose a collection strategy

<CollectionStrategy />

<Note>
  For multiple independent-account collection, repeat the single-account permission configuration for each account. Then mark one profile per account with `bloodhound_collect = true` in the AWS config file that you pass to the collector as `aws_config_file`.
</Note>

<Note>
  When the collector runs with EKS Pod Identity, EKS adds transitive session tags to its temporary credentials. AWS carries those tags through each `AssumeRole` hop. For every role the collector assumes, allow both `sts:AssumeRole` and `sts:TagSession` in the caller's permissions policy and the target role's trust policy. Keep the caller principal and target role resources scoped to the collector roles. The AWS-hosted examples below include `sts:TagSession` for EKS; omit it when the runtime credentials do not carry transitive session tags. If your authorization policies do not depend on these tags, you can instead [disable Pod Identity session tags](#troubleshoot-eks-session-tags).
</Note>

## Prerequisites

- AWS CLI v2.32.0 or later installed.
- Administrator access to the AWS account where you create the collector principal and IAM roles.
- For organization collection, access to the AWS Organizations management account or a delegated administrator account.
- For organization collection, CloudFormation StackSets enabled with trusted access for AWS Organizations.
- For AWS-hosted collection, a running EC2 instance or EKS cluster that hosts the OpenHound AWS collector.

## Authenticate to AWS

Run the following commands to authenticate to AWS with an administrative profile:

```bash
aws login --profile openhound-admin
export AWS_PROFILE=openhound-admin
aws sts get-caller-identity
```

The `aws sts get-caller-identity` command returns the AWS identity that creates the roles and policies in the following steps.

## Configure permissions

Click the tab that matches the AWS scope you want OpenHound to collect. Each path includes deployment model tabs for local or external workloads and AWS-hosted workloads.

<Tabs>
  <Tab title="Organization (source account)" icon="star">
    Use this recommended procedure when the collector's AWS identity is in a dedicated source account. The role-assumption path is:

    1. The source identity assumes the management-account role to list the organization's active accounts, read AWS Organizations metadata, and collect management-account resources.
    1. The management-account role assumes the collection role in each active member account.

    The source identity needs permission to assume only the management-account role. The management-account role needs permission to assume the member-account roles, and each member-account role trusts the management-account role.

    <Steps>
      <Step title="Create or identify the source principal">
        Create or identify the identity that the collector uses in the configured source account. Do not create this principal in the management account.

        <Tabs>
          <Tab title="Local or external workload">
            Create an IAM user named `OpenHoundCollectorUser` in the source account, or use an existing IAM user:

            ```bash
            aws iam create-user --user-name OpenHoundCollectorUser
            aws iam create-access-key --user-name OpenHoundCollectorUser
            ```
          </Tab>
          <Tab title="AWS-hosted workload">
            Create or identify the IAM role attached to the EC2 instance or EKS pod's service account that runs the collector in the source account. The examples below use `<WORKLOAD_ROLE_NAME>` as the workload role name.
          </Tab>
        </Tabs>
      </Step>
      <Step title="Create the management-account role">
        Create a role named `<MANAGEMENT_ROLE_NAME>` in the management account. Use the same value for `management_role_name` in the collector configuration.

        If you omit `management_role_name`, name this role the same as `collector_assumed_role_name`. Replace the principal with the source-account principal that runs the collector.

        <Tabs>
          <Tab title="Local or external workload">
            Save this trust policy as `management-role-trust.json`:

            ```json title="management-role-trust.json"
            {
              "Version": "2012-10-17",
              "Statement": [
                {
                  "Effect": "Allow",
                  "Principal": {
                    "AWS": "arn:aws:iam::<SOURCE_ACCOUNT_ID>:user/OpenHoundCollectorUser"
                  },
                  "Action": "sts:AssumeRole"
                }
              ]
            }
            ```
          </Tab>
          <Tab title="AWS-hosted workload">
            Save this trust policy as `management-role-trust.json`:

            ```json title="management-role-trust.json"
            {
              "Version": "2012-10-17",
              "Statement": [
                {
                  "Effect": "Allow",
                  "Principal": {
                    "AWS": "arn:aws:iam::<SOURCE_ACCOUNT_ID>:role/<WORKLOAD_ROLE_NAME>"
                  },
                  "Action": [
                    "sts:AssumeRole",
                    "sts:TagSession"
                  ]
                }
              ]
            }
            ```
          </Tab>
        </Tabs>

        Attach the `openhound-collector-policy.json` policy from above to the management-account role:

        ```bash
        aws iam create-role \
          --role-name <MANAGEMENT_ROLE_NAME> \
          --assume-role-policy-document file://management-role-trust.json \
          --max-session-duration 3600

        aws iam put-role-policy \
          --role-name <MANAGEMENT_ROLE_NAME> \
          --policy-name OpenHoundCollectorReadOnly \
          --policy-document file://openhound-collector-policy.json
        ```
      </Step>
      <Step title="Deploy the member-account role with StackSets">
        Use the `collector-role-stack.yaml` template and StackSets commands in the [Organization collection from the management account](/openhound/collectors/aws/configure-permissions#organization-management-account-2) tab.

        The member-account role trusts the management-account role, not the source principal. In the template's trust policy, set the principal to the role you created in the previous step:

        ```yaml
        Principal:
          AWS: "arn:aws:iam::<MANAGEMENT_ACCOUNT_ID>:role/<MANAGEMENT_ROLE_NAME>"
        ```

        If the source principal uses EKS Pod Identity, start from the AWS-hosted workload template, which also allows `sts:TagSession`: EKS session tags carry through the management-account role to every member-account role.

        Keep the OpenHound read-only policy attached to the member-account role. Deploy the role to every active member account that the collector should collect.
      </Step>
      <Step title="Allow the management-account role to assume member-account roles">
        Save the following document as `openhound-assume-member-roles.json`. Replace `<ORG_PATH>` with the AWS Organizations path that contains the target accounts, for example `o-exampleorgid/*` for the whole organization:

        ```json title="openhound-assume-member-roles.json"
        {
          "Version": "2012-10-17",
          "Statement": [
            {
              "Sid": "AssumeMemberCollectorRoles",
              "Effect": "Allow",
              "Action": [
                "sts:AssumeRole",
                "sts:TagSession"
              ],
              "Resource": "arn:aws:iam::*:role/OpenHoundCollectorRole",
              "Condition": {
                "ForAnyValue:StringLike": {
                  "aws:ResourceOrgPaths": [
                    "<ORG_PATH>"
                  ]
                }
              }
            }
          ]
        }
        ```

        Attach it to the management-account role:

        ```bash
        aws iam put-role-policy \
          --role-name <MANAGEMENT_ROLE_NAME> \
          --policy-name OpenHoundAssumeMemberRoles \
          --policy-document file://openhound-assume-member-roles.json
        ```
      </Step>
      <Step title="Allow the source principal to assume the management-account role">
        Save the following document as `openhound-assume-role.json`. For EKS Pod Identity, the source principal needs both `sts:AssumeRole` and `sts:TagSession`; otherwise you can omit `sts:TagSession`.

        ```json title="openhound-assume-role.json"
        {
          "Version": "2012-10-17",
          "Statement": [
            {
              "Sid": "AssumeManagementCollectorRole",
              "Effect": "Allow",
              "Action": [
                "sts:AssumeRole",
                "sts:TagSession"
              ],
              "Resource": "arn:aws:iam::<MANAGEMENT_ACCOUNT_ID>:role/<MANAGEMENT_ROLE_NAME>"
            }
          ]
        }
        ```

        Attach the policy to `OpenHoundCollectorUser` for a local or external workload, or to the workload role for an AWS-hosted workload.
      </Step>
      <Step title="Verify the source identity">
        Before configuring the collector, verify that the configured profile or runtime credentials resolve to the source principal that `management-role-trust.json` trusts:

        ```bash
        aws sts get-caller-identity --profile <SOURCE_PROFILE_NAME>
        ```

        If the collector uses runtime credentials, run the command from the same workload environment without `--profile`.
      </Step>
      <Step title="Configure the collector">
        <Tabs>
          <Tab title="Local or external workload">
            Create a source profile with the access keys from the `OpenHoundCollectorUser` user:

            ```bash
            aws configure --profile openhound-source
            ```

            Set `collector_profile_name` to that profile:

            ```toml title="~/.dlt/secrets.toml"
            [sources.source.aws.credentials]
            management_account_id = "<MANAGEMENT_ACCOUNT_ID>"
            management_role_name = "<MANAGEMENT_ROLE_NAME>"
            collector_assumed_role_name = "OpenHoundCollectorRole"
            collector_profile_name = "openhound-source"
            ```
          </Tab>
          <Tab title="AWS-hosted workload">
            Omit `collector_profile_name` so that the collector uses the workload role from its runtime:

            ```toml title="~/.dlt/secrets.toml"
            [sources.source.aws.credentials]
            management_account_id = "<MANAGEMENT_ACCOUNT_ID>"
            management_role_name = "<MANAGEMENT_ROLE_NAME>"
            collector_assumed_role_name = "OpenHoundCollectorRole"
            ```
          </Tab>
        </Tabs>
      </Step>
    </Steps>
  </Tab>
  <Tab title="Organization (management account)">
    Use this alternative when the AWS collector's identity resolves to the AWS Organizations management account and assumes a read-only collection role in member accounts.

    <Note>
      Run these setup steps from the AWS Organizations management account or a delegated administrator account. Before continuing, verify the active AWS identity with `aws sts get-caller-identity`. The collector's own identity must still be a role in the management account; a delegated administrator account cannot replace it.
    </Note>

    The AWS identity must resolve to credentials in the management account with permissions to read AWS Organizations metadata and assume `OpenHoundCollectorRole` in member accounts.

    The member-account roles trust `OpenHoundCollectorRole` in the management account, so create that role first. Do not deploy the member-account StackSet to the management account.

    <Steps>
      <Step title="Create the management-account collector role">
        In the management account, follow the [Single-account](/openhound/collectors/aws/configure-permissions#single-account-2) procedure through **Allow the collector principal to assume the collector role**. Its read-only policy also covers AWS Organizations and management-account collection. Skip its **Configure the AWS profile** step; this procedure configures the profile at the end.
      </Step>
      <Step title="Create or identify the management-account collector principal">
        <Tabs>
          <Tab title="Local or external workload">
            Create an IAM user named `OpenHoundCollectorUser` in the management account:

            ```bash
            aws iam create-user --user-name OpenHoundCollectorUser
            aws iam create-access-key --user-name OpenHoundCollectorUser
            ```

            Securely store the returned `AccessKeyId` and `SecretAccessKey`.
          </Tab>
          <Tab title="AWS-hosted workload">
            Create or identify the IAM role attached to the EC2 instance or EKS pod's service account that runs the collector from the management account.

            The examples in this page use `AttachedOpenHoundCollectorRole` as the workload role name.
          </Tab>
        </Tabs>
      </Step>
      <Step title="Save the member-account role template">
        Replace `<MANAGEMENT_ACCOUNT_ID>` with the AWS Organizations management account ID.

        <Tabs>
          <Tab title="Local or external workload">
            Save the following template as `collector-role-stack.yaml`:

            ```yaml title="collector-role-stack.yaml"
            AWSTemplateFormatVersion: "2010-09-09"
            Description: OpenHound read-only collector role

            Resources:
              OpenHoundCollectorRole:
                Type: AWS::IAM::Role
                Properties:
                  RoleName: OpenHoundCollectorRole
                  MaxSessionDuration: 3600
                  AssumeRolePolicyDocument:
                    Version: "2012-10-17"
                    Statement:
                      - Effect: Allow
                        Principal:
                          AWS: "arn:aws:iam::<MANAGEMENT_ACCOUNT_ID>:role/OpenHoundCollectorRole"
                        Action: sts:AssumeRole
                  Policies:
                    - PolicyName: OpenHoundCollectorReadOnly
                      PolicyDocument:
                        Version: "2012-10-17"
                        Statement:
                          - Sid: BaseCallerAndRegions
                            Effect: Allow
                            Action:
                              - sts:GetCallerIdentity
                              - ec2:DescribeRegions
                            Resource: "*"
                          - Sid: IAM
                            Effect: Allow
                            Action:
                              - iam:GetAccountAuthorizationDetails
                              - iam:ListSAMLProviders
                              - iam:ListOpenIDConnectProviders
                              - iam:GetSAMLProvider
                              - iam:GetOpenIDConnectProvider
                            Resource: "*"
                          - Sid: Organizations
                            Effect: Allow
                            Action:
                              - organizations:DescribeOrganization
            ```

## Troubleshoot EKS session tags

EKS Pod Identity enables session tags by default and passes them through subsequent role assumptions. A collector on Kubernetes can therefore receive `AccessDenied` for `sts:TagSession` when assuming a management or member-account role, even when `sts:AssumeRole` is allowed. Management-account authentication can succeed while member accounts are skipped if the later role assumptions reject the tags. This behavior applies to EKS Pod Identity; other Kubernetes credential methods do not automatically add these EKS tags.

Choose one of these configurations:

- Retain session tags and allow `sts:TagSession` alongside `sts:AssumeRole` in the caller permissions and target role trust for every role assumption, including management-to-member assumptions.
- Disable the automatic tags on the collector's Pod Identity association if your IAM authorization policies do not depend on them. OpenHound AWS does not require these tags to collect data.

To disable the tags, run the following command with an AWS identity authorized for `eks:UpdatePodIdentityAssociation`. Replace the placeholders with your cluster, association ID, and region:

```bash
aws eks update-pod-identity-association \
  --cluster-name <cluster-name> \
  --association-id <association-id> \
  --region <aws-region> \
  --disable-session-tags
```

Restart the collector deployment to obtain fresh credentials. The following command requires Kubernetes permission to patch the deployment:

```bash
kubectl -n <namespace> rollout restart deployment/<collector-deployment>
kubectl -n <namespace> rollout status deployment/<collector-deployment>
```

Run a new collection and check the logs for skipped accounts and role-assumption errors. Disabling tags resolves failures caused by the automatic EKS tags; each role still needs the appropriate `sts:AssumeRole` permissions and trust.

For details, see [AWS documentation on EKS Pod Identity session tags](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-abac.html).
