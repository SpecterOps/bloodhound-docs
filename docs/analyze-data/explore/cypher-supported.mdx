## Purpose

Use this reference to write queries in the Cypher subset supported by BloodHound Enterprise and BloodHound Community Edition. For an introduction and saved-query workflows, see [Search with Cypher](/analyze-data/explore/cypher-search).

This reference applies to BloodHound v9.10.0. PostgreSQL uses CySQL to translate Cypher into SQL; PostgreSQL-specific behavior and limitations are identified below.

BloodHound parses queries before execution. A construct accepted by Cypher grammar or available directly in Neo4j is not necessarily supported in BloodHound. Procedure calls and user-supplied query parameters are rejected by the application, regardless of the database backend.

## Identifiers and aliases

Use backticks to quote labels, relationship types, properties, variables, or aliases containing spaces, punctuation, or reserved words. A doubled backtick represents a literal backtick. Empty escaped property names are rejected.

```cypher
MATCH (n:User)
RETURN n.objectid AS objectId, n.`external-id` AS `External ID`
```

Result aliases preserve their requested case and decoded spelling, including through `WITH` and `ORDER BY`. Raw result consumers must use the requested column key, such as `objectId`.

## Pattern matching

### Node matching

Match all nodes, restrict labels, or use an inline property map:

```cypher
MATCH (n:User {name: 'ALICE@EXAMPLE.COM'})
RETURN n
```

```cypher
MATCH (n)
WHERE n.name = 'ALICE@EXAMPLE.COM'
RETURN n
```

Combine labels with `:`, as in `(n:User:Tag_Tier_Zero)`.

<Note>
  BloodHound represents Tier Zero membership with the `Tag_Tier_Zero` label. See [Write Custom Queries](/analyze-data/explore/cypher-search#write-custom-queries) for examples.
</Note>

### Relationship matching

Use `->` for outgoing, `<-` for incoming, and `-` without an arrowhead for undirected matching. Use `|` to match alternative relationship types:

```cypher
MATCH (:User)-[r:MemberOf|GenericWrite]->()
RETURN r
```

Unknown labels and relationship types produce no matches. A list of alternative relationship types can still match its known alternatives.

A relationship cannot repeat within one ordinary `MATCH`, including across comma-separated patterns and consecutive expansions. Separate `MATCH` clauses have separate uniqueness scopes. Reusing a bound node or fixed relationship variable matches that entity by identity.

### Recursive expansion

Variable-length patterns follow multiple relationships. Bounds are inclusive:

| Syntax | Relationship count |
| --- | --- |
| `*` or `*..` | One or more, with no upper bound |
| `*k` | Exactly `k`, equivalent to `*k..k` |
| `*k..` | At least `k`, with no upper bound |
| `*..k` | One through `k` |
| `*m..n` | `m` through `n` |
| `*0..0` | Zero; the start and end are the same node |

```cypher
MATCH p = (:User)-[r:MemberOf*1..3]->(:Group)
RETURN p, r
```

A variable-length relationship binding such as `r` is a list of relationships. A path binding such as `p` includes the ordered nodes and relationships.

An omitted upper bound has no implicit 15-hop cutoff. Open-ended queries can return paths beyond 15 hops and remain subject to execution budgets and cancellation. Budget exhaustion produces an error rather than a successful truncated result.

Use an explicit bound such as `*1..15` if you intend to search only that depth. This also limits which entities a mutation can reach.

### Pattern projections and bound endpoints

Bind a path to return it or use path functions:

```cypher
MATCH p = (:Computer)-[:HasSession]->(:User)
RETURN p
```

Multiple reading clauses can reuse a bound endpoint on either side of a pattern:

```cypher
MATCH (e:User)
MATCH p = ()-[]->(e)
RETURN p
LIMIT 1
```

### Optional match

`OPTIONAL MATCH` preserves an incoming row when its pattern does not match, setting newly introduced bindings to null. Repeated input rows retain their multiplicity.

```cypher
MATCH (u:User)
OPTIONAL MATCH (u)-[:MemberOf]->(g:Group)
RETURN u.name, g.name
```

A `WHERE` attached to the optional match restricts that match while retaining unmatched incoming rows. Filtering later with `WITH ... WHERE` can remove those rows:

```cypher
MATCH (u:User)
OPTIONAL MATCH (u)-[:MemberOf]->(g:Group)
WHERE g.name = 'DOMAIN ADMINS@EXAMPLE.COM'
WITH u, g
WHERE g IS NOT NULL
RETURN u, g
```

A leading `OPTIONAL MATCH` starts with one implicit row. If nothing matches, it can return one row with null bindings.

### Shortest paths

`shortestPath` returns one minimum-length trail per endpoint pair. A trail does not repeat a relationship. When multiple trails tie, the selected trail is unspecified.

```cypher
MATCH p = shortestPath((u:User)-[*1..]->(:Domain))
WHERE u.objectid = 'UUID-1234-567890'
RETURN p, length(p)
```

### All shortest paths

`allShortestPaths` returns all relationship-distinct minimum-length trails per endpoint pair. Returning every tied trail can require substantially more resources.

```cypher
MATCH p = allShortestPaths((u:User)-[*1..]->(:Domain))
WHERE u.objectid = 'UUID-1234-567890'
RETURN p
```

Bind shortest paths in `MATCH` before using them. Expression forms such as `RETURN length(shortestPath(...))` are unsupported. See [Known limitations](#known-defects) for PostgreSQL direction, bound, and mutation restrictions.

## Build multi-part queries

`WITH` passes only its projected bindings to the next query part. It supports aliases, `DISTINCT`, aggregation, filtering, sorting, and pagination. Constant projections preserve the incoming row count.

```cypher
MATCH (u:User)
WITH u ORDER BY u.name LIMIT 5
MATCH p = (u)-[:MemberOf]->(g:Group)
RETURN p
```

`ORDER BY`, `SKIP`, and `LIMIT` on `WITH` apply at that boundary, before its `WHERE` filters the output. Later `WITH` and `RETURN` projections have their own modifiers.

## Result ordering and pagination

### `ORDER BY`

Sort by projection aliases or supported expressions. Ascending order is the default; append `DESC` for descending order.

```cypher
MATCH (u:User)
RETURN u.name AS userName
ORDER BY userName DESC
LIMIT 10
```

### `SKIP` and `LIMIT`

Use these clauses with `RETURN` or `WITH` to skip or limit rows after sorting. PostgreSQL requires literal counts; calculated and parameterized counts are unsupported.

```cypher
MATCH (n:User)
RETURN n
ORDER BY n.name
SKIP 10
LIMIT 100
```

## Entity creation[](#entity-creation)

<CypherMutationsNote clause="CREATE" />

Create nodes and relationships with property maps. Property values retain their types; null-valued properties are omitted.

```cypher
CREATE (u:User {name: 'ALICE@EXAMPLE.COM', enabled: true})
  -[r:MemberOf]->(g:Group {name: 'ADMINS@EXAMPLE.COM'})
RETURN u, r, g
```

Supported mutations preserve incoming rows. Multipart writes execute transactionally, and later query parts can observe earlier writes.

## Entity updates[](#entity-updates)

<CypherMutationsNote clause="SET and REMOVE" />

Set properties and add labels with `SET`; remove them with `REMOVE`:

```cypher
MATCH (n:User)
SET n.reviewed = true
REMOVE n.old_property
RETURN n
```

```cypher
MATCH (n:Base)
WHERE n.obviously_is_user
SET n:User
REMOVE n:OldLabel
RETURN n
```

```cypher
MATCH ()-[r:HasSession]->(:User)
SET r.reviewed = true
REMOVE r.old_property
RETURN r
```

PostgreSQL preserves the order of `SET` and `REMOVE` intents, but an assignment expression in the same query part can still read an earlier property value. Insert a `WITH` boundary before an assignment that depends on a preceding update:

```cypher
MATCH (n:User)
SET n.x = 1
REMOVE n.x
WITH n
SET n.y = coalesce(n.x, -1)
RETURN n.y
```

## Entity deletion[](#entity-deletion)

<CypherMutationsNote clause="DELETE and DETACH DELETE" />

`DELETE` removes relationships or disconnected nodes. Deleting a connected node with plain `DELETE` fails and rolls back. `DETACH DELETE` also removes the node's incident relationships.

```cypher
MATCH ()-[r:MemberOf]->()
DELETE r
```

Capture values before deleting their entity. Deletion can be followed by scalar or count projections:

```cypher
MATCH (n:User)
WHERE n.objectid = 'UUID-1234-567890'
WITH n, n.name AS deletedName
DETACH DELETE n
RETURN deletedName
```

## Unwind a list into rows

`UNWIND` expands one list level into rows. It accepts literal lists, property arrays, and collected lists, preserving element types. Duplicate elements produce duplicate rows. The target variable must not shadow an existing binding.

```cypher
UNWIND ['ALICE@EXAMPLE.COM', 'BOB@EXAMPLE.COM'] AS userName
MATCH (u:User)
WHERE u.name = userName
RETURN u
```

You can follow `UNWIND` with matching, aggregation, sorting, or mutation clauses. Empty, null, and missing dynamic inputs produce no rows; a non-list property value produces one row.

```cypher
MATCH (u:User)
WHERE u.name CONTAINS 'A'
WITH collect(u.name) AS names
UNWIND names AS userName
RETURN userName
LIMIT 100
```

This second example returns scalar values; `UNWIND` does not itself restrict queries to scalar results.

## Supported query filters

### Comparison expressions

Supported comparisons are `=`, `<>`, `<`, `>`, `<=`, and `>=`. For PostgreSQL property typing rules, see [Backend differences](#cysql-differences).

### Null, membership, and label predicates

Use `IS NULL` or `IS NOT NULL` to test absence. Missing properties, stored null properties, and unmatched optional bindings satisfy `IS NULL`. Do not use `= null` to check absence.

```cypher
MATCH (n:User)
WHERE n.description IS NULL
RETURN n
```

```cypher
RETURN null IS NULL AS value
```

Use `IN` for list membership, and `n:User` to test a node label:

```cypher
MATCH (n)
WHERE n:User AND n.name IN ['ALICE@EXAMPLE.COM', 'BOB@EXAMPLE.COM']
RETURN n
```

Collected nodes and relationships support identity-based membership:

```cypher
MATCH (n:User)
WHERE NOT n.enabled
WITH collect(n) AS disabled
MATCH p = (:Computer)-[:HasSession]->(u:User)
WHERE NOT (u IN disabled)
RETURN p
LIMIT 1
```

Nodes, relationships, and numeric IDs remain distinct types even when their IDs have the same numeric value. This membership support does not imply arbitrary comparisons between entity-list expressions.

Empty property-list equality and empty lists carried through `WITH` or `UNWIND` are supported:

```cypher
MATCH (n:User)
WHERE n.auth_modes = []
RETURN n
```

### Boolean expressions

Use `AND`, `OR`, `XOR`, and `NOT`. For non-null Boolean operands, `XOR` is true when exactly one operand is true. Null operands can produce null results.

```cypher
MATCH (n:User)
WHERE (n.enabled XOR n.hasspn) AND NOT n.lockedout
RETURN n
```

Parentheses preserve grouping. Repeated `NOT` preserves parity: two negations cancel, and three act as one. Boolean expressions also work as values in `RETURN`, `WITH`, function arguments, and `SET`; they filter rows only when used in `WHERE`.

### String searching

`STARTS WITH`, `CONTAINS`, and `ENDS WITH` are case-sensitive, literal string tests. `%`, `_`, and backslashes are not wildcard characters, including after supported functions and aliases.

```cypher
MATCH (n:User)
WHERE n.name STARTS WITH 'ALICE' OR n.name ENDS WITH '@EXAMPLE.COM'
RETURN n
```

```cypher
MATCH (n:User)
WHERE n.description CONTAINS 'service account'
RETURN n
```

PostgreSQL string predicates require strings. Non-string property operands yield null rather than matching an automatic text conversion. Use `toString` when you intend a textual comparison.

### Regular expressions

Use `=~` for regex matching:

```cypher
MATCH (n:User)
WHERE n.name =~ '^ALICE.*@EXAMPLE[.]COM$'
RETURN n
```

On PostgreSQL, `=~` uses PostgreSQL regex syntax and searches for a matching substring. Add `^` and `$` when you intend to match the whole string. Do not assume complete compatibility with Neo4j's Java regex syntax.

### Pattern predicates

Use fixed-length patterns in filters, for example to find users without sessions:

```cypher
MATCH (n:User)
WHERE NOT ((n)<-[:HasSession]-(:Computer))
RETURN n
```

Recursive expansion inside pattern predicates is unsupported. The PostgreSQL aggregate traversal-count optimization also has a specific [pattern-predicate limitation](#known-defects).

## Quantifier expressions

Use quantifiers in `WHERE` to test a predicate for list elements:

| Quantifier | True when |
| --- | --- |
| `any` | At least one element satisfies the predicate |
| `single` | Exactly one element satisfies the predicate |
| `none` | No element satisfies the predicate |
| `all` | Every element satisfies the predicate |

```cypher
MATCH (n:User)
WHERE any(spn IN n.serviceprincipalnames WHERE toUpper(spn) CONTAINS 'HTTP')
RETURN n
```

Replace `any` with `single`, `none`, or `all` to apply the other tests. PostgreSQL does not support scalar quantifier projections such as `RETURN all(x IN [1] WHERE x = 1)` or corresponding `WITH` projections; they return translation errors.

## Arithmetic expressions

Numeric arithmetic supports `+`, `-`, `*`, `/`, `%`, and `^`. Addition also supports string concatenation and list addition.

```cypher
MATCH (n:User)
RETURN n.logoncount + n.badpwdcount AS combinedCount
```

```cypher
MATCH (n:User)
WITH n.logoncount AS logons, n.badpwdcount AS failures
RETURN logons + failures AS combinedCount
```

PostgreSQL arithmetic on dynamic properties uses their stored types. Integer division truncates toward zero. Missing or null operands yield null; incompatible operands and integer overflow produce query errors. See [Known limitations](#known-defects) for remaining property-alias expression restrictions.

## Aggregate functions

Aggregate functions summarize rows in `RETURN` or `WITH`. Non-aggregate projected expressions define groups:

```cypher
MATCH (u:User)
RETURN u.enabled, count(*) AS users
```

| Function | Behavior |
| --- | --- |
| `count(*)` | Counts rows |
| `count(expr)` | Counts non-null values; supports `count(DISTINCT expr)` |
| `collect(expr)` | Builds a list of non-null values, preserving their types; supports `collect(DISTINCT expr)` |
| `sum(expr)` | Sums numeric values; supports `sum(DISTINCT expr)` |
| `avg(expr)` | Computes an average using floating-point conversion |
| `min(expr)`, `max(expr)` | Select minimum and maximum values |

`collect` excludes missing/null values and returns an empty list for empty or all-null input. `sum` ignores nulls, returns integer zero for empty or all-null input, and preserves signed 64-bit integer precision for integer sums. Floating-point or mixed numeric inputs use floating-point arithmetic. Nonnumeric input and integer overflow produce errors. `avg` returns null for empty input. Empty grouped input produces no groups.

```cypher
MATCH (u:User)
RETURN min(u.logoncount), max(u.logoncount), min(u.name), max(u.name)
```

These are functions, not support for `COLLECT { ... }` or `COUNT { ... }` subqueries.

## Supported Cypher functions[](#supported-cypher-functions)

### Temporal functions

| Function | No-argument result | Text construction example |
| --- | --- | --- |
| `date()` | Current date, without a time zone | `date('2020-01-01')` |
| `datetime()` | Current timestamp with time zone | `datetime('2020-01-01T00:00:00Z')` |
| `localdatetime()` | Current timestamp without time zone | `localdatetime('2020-01-01T00:00:00')` |
| `localtime()` | Current time without time zone | `localtime('12:00:00')` |

`duration` requires a string literal. Use durations in temporal arithmetic:

```cypher
MATCH (n)
WHERE n.created_at < date() - duration('P1D')
RETURN n
```

Current-instant `.epochseconds` and `.epochmillis` access are supported. For example, for a password timestamp stored in epoch seconds:

```cypher
MATCH (u:User)
WHERE u.pwdlastset < datetime().epochseconds - (180 * 86400)
RETURN u
```

General calendar components such as `.year` are unsupported. Components on explicitly constructed values, such as `date('2020-01-01').year` and `datetime('2020-01-01').epochmillis`, return translation errors. Temporal map constructors are outside the supported subset.

### `id` function

Returns a node or relationship identifier:

```cypher
MATCH (n:User)
WHERE id(n) IN [1, 2, 3, 4]
RETURN n
```

### `labels` function

Returns a node's label names as a list of strings:

```cypher
MATCH (n)
RETURN labels(n)
```

Prefer label patterns such as `MATCH (n:User)` for ordinary label filtering.

### `type`

Returns a relationship's type as text. Prefer a typed pattern for ordinary filtering:

```cypher
MATCH ()-[r:MemberOf]->()
RETURN type(r)
```

### String and conversion functions

| Function | Behavior |
| --- | --- |
| `split(value, delimiter)` | Splits a string into a list of strings |
| `toLower(value)` | Returns a lowercase string |
| `toUpper(value)` | Returns an uppercase string |
| `toString(value)` | Converts a supported value to text |
| `toInteger(value)` | Converts a supported value to an integer |

String functions require string inputs; unsupported conversions can raise errors. PostgreSQL also accepts the legacy spelling `toint` for `toInteger`.

`toInteger` truncates numeric inputs toward zero: `1.9` becomes `1`, and `-1.5` becomes `-1`. Integer inputs preserve signed 64-bit precision. Invalid strings and out-of-range conversions remain compatibility limits; do not rely on Neo4j's failure behavior.

```cypher
MATCH (u:User)
RETURN split(u.name, '@'), toLower(u.name), toInteger(u.logoncount)
```

### `coalesce`

Returns the first non-null value:

```cypher
MATCH (n:User)
WITH coalesce(n.description, '') AS description
RETURN description
```

PostgreSQL preserves the selected dynamic property's type through `WITH`, including when a fallback has a different type. Statically typed argument combinations can still have compatibility restrictions.

### `size`

Counts list elements or Unicode characters in a string. Direct properties and values carried through `WITH` are supported; null input remains null.

```cypher
MATCH (u:User)
WITH u.name AS userName, u.serviceprincipalnames AS spns
RETURN size(userName), size(spns)
```

### `length`

Returns the relationship count of a bound path:

```cypher
MATCH p = (a)-[:MemberOf*1..3]->(b)
RETURN length(p)
```

### `nodes`

Returns the ordered node list of a matched path:

```cypher
MATCH p = ()-[]->()
RETURN nodes(p)
```

### `relationships`

Returns the ordered relationship list of a matched path:

```cypher
MATCH p = ()-[]->()
RETURN relationships(p)
```

### `startNode`

Returns a relationship's start node:

```cypher
MATCH p = (a)-[*1..3]->(b)
WHERE none(r IN relationships(p) WHERE startNode(r).name = 'BLOCKED')
RETURN p
```

### `endNode`

Returns a relationship's end node:

```cypher
MATCH ()-[r]->()
RETURN endNode(r)
```

### `head`

Returns the first list element:

```cypher
MATCH p = ()-[]->()
RETURN head(nodes(p))
```

### `tail`

Returns all list elements except the first:

```cypher
MATCH p = ()-[]->()
RETURN tail(nodes(p))
```

## Known limitations

The following PostgreSQL restrictions remain in v9.10.0:

- Generic undirected shortest-path searches and shortest-path minimum bounds greater than one are unsupported.
- Bounded `allShortestPaths` with equal endpoints and a minimum of zero can return no row instead of a zero-hop path.
- `shortestPath` followed by `SET ... RETURN p` can lose the path representation.
- Scalar quantifier projections in `RETURN` or `WITH` return translation errors.
- Pattern predicates in the optimized aggregate traversal-count shape (`MATCH ... WITH s, count(t) AS c RETURN ... ORDER BY ... LIMIT ...`) fail with `unsupported aggregate traversal count predicate: pattern predicates in MATCH WHERE are not supported`. This does not prohibit all aggregates combined with pattern predicates.
- Unary negation of a carried property in sorting, such as `RETURN n.logoncount AS x ORDER BY -x`, can fail with PostgreSQL's unsupported `- jsonb` operation.
- Some property-arithmetic alias filters remain unsupported; support for arithmetic projections does not establish support for every later alias filter.
- Same-part assignment expressions can read earlier property values. Use the [update boundary example](#entity-updates) for dependent assignments.
- Literal-only `SKIP`/`LIMIT`, temporal components, invalid conversions, and list typing retain the restrictions described above. Mixed-type literal lists are not generally supported.

### Open traversal execution budgets

PostgreSQL open traversal defaults to 100,000 candidate states and 64 MiB of cumulative estimated trail state. Exhaustion raises SQLSTATE `54000`. These are execution accounting limits, not a depth cutoff or a measured process-memory cap.

For DAWGS operators, positive `dawgs.traversal_state_limit` and `dawgs.traversal_byte_limit` session or transaction settings control these budgets. They are not BloodHound configuration-file options. Deploying the upgraded compiler requires the matching DAWGS schema helpers.

## Unsupported constructs[](#unsupported-constructs)

The following constructs are outside BloodHound's supported subset and return parse or translation errors:

- `CASE` expressions
- List and pattern comprehensions
- Existential subqueries and `COLLECT { ... }` / `COUNT { ... }` subqueries
- `MERGE`
- Recursive expansion inside pattern predicates
- List indexing, including negative, parameterized, or chained indexes; use `head` or `tail` where sufficient
- List slicing, including omitted or negative bounds
- `UNION` and `UNION ALL`
- Standalone and in-query `CALL`, including procedure arguments and `YIELD`
- `LOAD CSV` and `CREATE UNIQUE`
- Shortest paths in expression positions; bind the path in `MATCH` instead
- `FOREACH`, `REDUCE`, legacy `START`, `EXPLAIN`, `PROFILE`, and periodic/bulk-import clauses

## Backend differences

### Property types and numeric results

PostgreSQL scalar equality uses stored property types rather than assuming that a string compared to a number must be parsed as an integer. Numeric-looking strings remain strings.

For ordered dynamic-property comparisons, numbers compare numerically, strings by Unicode order, Booleans with false before true, and lists lexicographically. Incompatible types and null operands yield null. Values carried through `WITH` preserve their stored types. Native casts and functions still have specific type restrictions; this is not complete Neo4j type compatibility.

Raw PostgreSQL results preserve signed 64-bit integers and floating-point values. Stored JSON can erase the distinction between an integral float and an integer; queries cannot recover type information already lost during storage.

### Index utilization

PostgreSQL property indexes do not require a label specifier. If `name` is indexed, both queries can use that index:

```cypher
MATCH (n:User)
WHERE n.name = 'ALICE@EXAMPLE.COM'
RETURN n
```

```cypher
MATCH (n)
WHERE n.name = 'ALICE@EXAMPLE.COM'
RETURN n
```

### Null behavior

`WHERE` retains only rows whose predicate evaluates to true. Projecting a missing or null property through `WITH` keeps it null; equality does not become true, so a later filter removes the row:

```cypher
MATCH (n:User)
WITH n.name AS userName
WHERE userName = 'ALICE@EXAMPLE.COM'
RETURN userName
```

Use `IS NULL` to check absence and `coalesce` to select a fallback explicitly:

```cypher
MATCH (n:User)
WHERE coalesce(n.description, '') CONTAINS 'service account'
RETURN n
```
