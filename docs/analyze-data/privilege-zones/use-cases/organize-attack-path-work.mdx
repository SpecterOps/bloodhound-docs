Large organizations often struggle with ownership. The team that sees the attack path may not own the system, identity provider, endpoint management platform, cloud account, source code repository, or application that needs remediation.

Privilege Zones and labels can help organize attack path work around the way the business operates.

## Scenario

A large enterprise has multiple business units, domains, platform teams, and infrastructure owners. The security team needs to understand whether one business unit can create attack paths into another, and which teams should own remediation.

The team uses labels to organize domains, systems, or objects by business unit. It then uses zones to analyze the most important boundaries. This allows the team to ask operational questions, such as:

- Can Business Unit A control systems in Business Unit B?
- Which attack paths are owned by a specific infrastructure team?
- Which domains or systems should be included in a business owner's remediation view?
- Which teams are inheriting risk from another team's systems or identity relationships?

## What this can reveal

- Cross-business-unit attack paths
- Centralized admin groups with broader reach than intended
- Business units inheriting risk from shared infrastructure
- Platform teams creating downstream exposure for application teams
- Remediation work that requires more than one team to coordinate

## Why this works

In large organizations, attack path remediation is a people and process problem as much as a technical problem. Zones and labels help localize the work. They allow teams to create views that map to ownership, instead of forcing all remediation into one enterprise-wide queue.

This becomes more important as organizations add technologies into BloodHound Enterprise through OpenGraph. As identity, source code, endpoint management, SaaS, and cloud systems appear in the graph, attack paths may cross team boundaries more frequently.

## Suggested workflow

1. Identify ownership boundaries that matter to the organization.
1. Create labels for business units, domains, platform teams, or application owners.
1. Use zones to define the most important assets or boundaries.
1. Analyze whether attack paths cross those boundaries.
1. Review findings with the teams that own the source and target systems.
1. Use the results to drive remediation and clarify accountability.

## Starter Cypher queries

<StarterQueriesCallout />

### Business unit discovery by naming convention

```cypher
MATCH (n)
WHERE toUpper(coalesce(n.name, '')) CONTAINS 'BU-NAME'
   OR toUpper(coalesce(n.name, '')) CONTAINS 'BUSINESS-UNIT'
   OR toUpper(coalesce(n.name, '')) CONTAINS 'REGION-NAME'
   OR toUpper(coalesce(n.name, '')) CONTAINS 'PLATFORM-NAME'
RETURN n
LIMIT 1000
```

### Ownership discovery by application or platform name

```cypher
MATCH (n)
WHERE toUpper(coalesce(n.name, '')) CONTAINS 'SAP'
   OR toUpper(coalesce(n.name, '')) CONTAINS 'ORACLE'
   OR toUpper(coalesce(n.name, '')) CONTAINS 'WORKDAY'
   OR toUpper(coalesce(n.name, '')) CONTAINS 'SALESFORCE'
RETURN n
LIMIT 1000
```

### Paths between two tagged or tiered boundaries

```cypher
// Replace Tag_BU_A / Tag_BU_B with your two business-unit zone tag labels.
MATCH p=(s:Tag_BU_A)-[:AD_ATTACK_PATHS*1..]->(t:Tag_BU_B)
RETURN p
LIMIT 1000
```

## Guidance

The security team may not own the remediation path for every finding. Privilege Zones work best when they create a shared operating model across security, IAM, infrastructure, application, endpoint, source code, and platform teams.

## Key takeaway

Privilege Zones and labels help large organizations convert attack path visibility into ownership, accountability, and cross-functional remediation.
