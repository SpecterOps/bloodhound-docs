Privilege Zones and labels help large organizations translate attack path visibility into ownership and action. Use this approach when remediation needs to follow business units, platform teams, application owners, or shared infrastructure domains.

In large environments, remediation is often an ownership problem as much as a technical problem. The team that identifies an attack path is not always the team that owns the identity provider, endpoint platform, cloud account, repository, or application that needs to change.

## Model how work gets assigned

Use zones to define protected boundaries. Use labels to add flexible context that helps teams triage and assign work across multiple dimensions.

| Use | Recommended tool | Reason |
| --- | ---------------- | ------ |
| Protected boundary | Zone | BloodHound uses zones in attack path and posture analysis. |
| Owner or business unit | Label | Objects can have multiple labels at the same time. |
| Campaign, status, or exception | Label | Labels help you filter and query without changing zone priority. |
| Cross-boundary analysis | Zone and label | Use both to understand impact and assign remediation. |

This model helps you answer practical questions:

- Which team owns the risk?
- Does one boundary create control over another boundary?
- Where does remediation require cross-team coordination?
- Which ownership areas need focused review?

## Account for connected technologies

As BloodHound includes more identity providers, developer platforms, endpoint systems, and custom OpenGraph data, attack paths increasingly cross ownership boundaries. Privilege Zones and labels give your teams a shared language for discussing those paths without reducing the work to one enterprise-wide queue.

## Use this approach when

- Different teams own different parts of the environment.
- Cross-boundary attack paths are hard to assign or remediate.
- You want views that align to ownership instead of only technology.
- Security, IAM, infrastructure, application, endpoint, and platform teams need a shared operating model.

## Move from concept to configuration

Create [zones](/analyze-data/privilege-zones/zones) for boundaries that deserve attack path analysis. Create [labels](/analyze-data/privilege-zones/labels) for ownership and triage dimensions. Use [rules](/analyze-data/privilege-zones/rules) to keep zone and label membership aligned with your environment.
