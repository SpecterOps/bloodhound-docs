Privilege Zones help you treat high-impact source code and deployment boundaries as protected operating boundaries. Use this approach when GitHub permissions influence production systems, infrastructure, secrets, or release workflows.

In source code platforms, the most important asset is not always a single repository. A repository can be sensitive because it contains important code, triggers workflows, deploys infrastructure, publishes production artifacts, accesses secrets, or assumes cloud roles. The protected boundary is often the software delivery path, not only the code itself.

## Model GitHub as a control plane

A GitHub-focused Privilege Zone can represent objects that influence production or other high-impact systems.

Common examples include:

- Repositories that contain production code or infrastructure-as-code
- Workflows that build, publish, deploy, or rotate sensitive material
- Environments, secrets, and variables that affect deployment behavior
- Teams and roles that administer high-impact repositories
- Applications or integrations that can change repository or workflow behavior

This framing helps your team analyze who can control the GitHub objects that matter most and how those paths connect to broader identity, cloud, infrastructure, or application risk.

## Use this approach when

- A repository or workflow can influence production systems.
- GitHub permissions are part of the deployment or infrastructure trust chain.
- You need to understand who can control high-impact repositories or workflows.
- You want to connect source code risk to broader attack path analysis.

## Move from concept to configuration

Use the [GitHub OpenGraph extension](/opengraph/extensions/github/overview) to model GitHub organizations, identities, repositories, workflows, secrets, roles, and related relationships in BloodHound. Then use the [GitHub Privilege Zone rules](/opengraph/extensions/github/privilege-zone-rules) as a starting point for classifying high-value GitHub assets.

After GitHub data is available, create a [zone](/analyze-data/privilege-zones/zones) for the protected GitHub boundary and define [rules](/analyze-data/privilege-zones/rules) that match the relevant repositories, workflows, teams, and roles.
